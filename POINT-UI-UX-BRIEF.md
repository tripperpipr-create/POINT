# Point — UI/UX Improvement Agent Prompt

> Статус: исторический рабочий бриф для UI/UX-итераций августа 2026 года. Он
> задаёт цели и порядок работы, но не является источником текущих возможностей,
> архитектуры или метрик. Актуальные документы перечислены в
> [docs/README.md](docs/README.md).

Ты работаешь над проектом **Point**.

Твоя задача — последовательно улучшать **визуальную часть, UX, удобство использования и качество UI-кода** двух основных компонентов продукта:

1. **Point IDE**
2. **Agent Hub**

Работа выполняется **итерациями/циклами примерно раз в час**. Каждый цикл должен быть небольшим, контролируемым и законченным:

**анализ → выбор конкретных проблем → реализация → проверка → отчёт**

Главная цель — постепенно довести интерфейс Point до уровня зрелого профессионального developer tool, не ломая существующую функциональность и не затрагивая ядро продукта.

---

# 1. КРИТИЧЕСКИЕ ОГРАНИЧЕНИЯ

## Не трогать ядро

**Не изменяй ядро Point, бизнес-логику, архитектуру backend/runtime, механику агентов, orchestration, API-контракты, storage, protocol layer и другую функциональность, не относящуюся непосредственно к UI/UX.**

Если во время работы обнаруживается:

- баг в ядре;
- архитектурная проблема;
- ошибка бизнес-логики;
- проблема в API;
- проблема взаимодействия сервисов;
- race condition;
- проблема storage;
- проблема orchestration;
- потенциальная потеря данных;
- ошибка состояния;
- некорректная работа runtime;
- проблема производительности, требующая изменения ядра;
- неправильное поведение функциональности;

**не исправляй её самостоятельно.**

Вместо этого зафиксируй проблему отдельно:

- файл / компонент / модуль;
- описание;
- как воспроизводится;
- почему это считается ошибкой;
- предполагаемая причина;
- потенциальное направление исправления;
- severity: `low / medium / high / critical`.

После фиксации продолжай работу над UI.

# 2. КАЧЕСТВО КОДА — ОБЯЗАТЕЛЬНОЕ ТРЕБОВАНИЕ

Все изменения должны быть реализованы **архитектурно правильно**.

Красивый интерфейс, реализованный плохим кодом, **не считается успешным результатом**.

Визуальная задача не является оправданием для технических костылей.

Запрещено без объективной необходимости:

- хаотично добавлять CSS overrides;
- использовать `!important` как стандартный способ решения проблем;
- hardcode'ить координаты и размеры;
- создавать абсолютное позиционирование там, где нужен нормальный layout;
- копировать одинаковую логику между компонентами;
- дублировать стили;
- создавать огромные монолитные компоненты;
- смешивать UI, бизнес-логику и инфраструктурную логику;
- обходить существующие abstractions проекта;
- создавать параллельные системы вместо использования уже существующих;
- добавлять технический долг ради быстрого визуального результата;
- менять ядро ради удобства реализации UI;
- отключать typecheck/lint/tests;
- скрывать ошибки вместо их исправления.

Перед каждым изменением сначала изучи существующую реализацию и определи, **где архитектурно должно находиться изменение**.

Переиспользуй существующие:

- UI components;
- layout primitives;
- design system;
- design tokens;
- hooks;
- utilities;
- state management;
- abstractions;
- project conventions;
- existing libraries.

Если существующей abstraction недостаточно, допускается аккуратно расширять **UI-слой**, если это не затрагивает ядро и не ломает существующие контракты.

# 3. НЕ ПЕРЕПИСЫВАТЬ РАБОТАЮЩИЙ КОД БЕЗ ПРИЧИНЫ

Не используй задачу по улучшению UI как повод провести глобальный рефакторинг проекта.

Если существующий компонент работает нормально и его можно улучшить небольшим чистым изменением — выбери этот вариант.

Большой рефакторинг допустим только внутри UI-слоя и только если существующая реализация объективно мешает:

- устранению визуальных багов;
- реализации нужного UX;
- поддерживаемости;
- расширяемости;
- консистентности UI;
- нормальной организации layout/state.

Даже в таком случае изменения должны быть максимально локализованы.

# 4. POINT IDE

Основной UX и visual reference — **современные IDE JetBrains**.

Не нужно слепо копировать JetBrains.

Нужно перенять удачные принципы:

- организации рабочего пространства;
- tool windows;
- dockable panels;
- редактора;
- терминалов;
- навигации;
- плотности интерфейса;
- управления большим количеством инструментов;
- минимального визуального шума.

Point IDE должна выглядеть:

- современно;
- минималистично;
- аккуратно;
- профессионально;
- цельно;
- удобно для длительной работы.

Интерфейс должен ощущаться как **developer tool**, а не как обычный dashboard или маркетинговый web app.

# 5. ВЕРХНЯЯ ПАНЕЛЬ IDE

Верхняя панель по умолчанию должна быть максимально компактной.

На ней должны находиться только действительно часто используемые действия.

Например:

- Run;
- Stop;
- Debug;
- выбранная run configuration;
- Search;
- основные действия проекта;
- несколько наиболее востребованных инструментов.

Не пытайся разместить наверху весь функционал приложения.

Редко используемые функции должны быть доступны через:

- dropdown;
- меню;
- command palette;
- context menu;
- дополнительные панели;
- расширяемый toolbar.

Пользователь должен иметь возможность при необходимости расширить верхнюю панель или настроить её.

Toolbar не должен превращаться в длинный ряд мелких иконок без понятной структуры.

Для неочевидных icon-only действий должны быть tooltip.

# 6. БОКОВЫЕ ПАНЕЛИ IDE

IDE должна использовать концепцию **tool windows**, близкую по UX к JetBrains.

На боковых панелях могут находиться:

- Project / File Explorer;
- Git;
- Search;
- Structure;
- SSH;
- Databases;
- AI / Agent tools;
- Docker;
- Kubernetes;
- дополнительные инструменты Point.

Tool windows должны по возможности поддерживать:

- открытие;
- закрытие;
- collapse;
- resize;
- изменение порядка;
- перемещение между левой и правой сторонами;
- сохранение понятного active state;
- компактное представление в закрытом состоянии.

Рабочая область редактора должна оставаться основной визуальной зоной.

Боковые панели не должны постоянно съедать пространство, если пользователь ими не пользуется.

# 9. LAYOUT-АРХИТЕКТУРА IDE

Не реализуй IDE через набор случайных абсолютных координат.

Для основных областей используй нормальную layout-архитектуру:

- flex;
- grid;
- resizable containers;
- split panes;
- dockable panels;
- constraints;
- shared sizing rules.

Состояния открытия, закрытия, resize и перемещения панелей должны иметь понятную модель, а не состоять из независимых CSS-хаков.

Если в проекте уже существует layout system или panel manager — используй его.

Не создавай второй конкурирующий механизм без серьёзной причины.

---

# 10. ВИЗУАЛЬНЫЙ СТИЛЬ POINT IDE

Основной принцип:

**минимум визуального шума + максимум полезного рабочего пространства + предсказуемое поведение интерфейса**

Особое внимание уделяй:

- visual hierarchy;
- spacing;
- typography;
- размеру элементов;
- border radius;
- hover;
- active;
- focus;
- selected states;
- contrast;
- separators;
- backgrounds;
- shadows;
- icons;
- density;
- information hierarchy.

Избегай:

- чрезмерного количества рамок;
- ярких акцентных цветов без смысла;
- огромных кнопок;
- больших пустых блоков без причины;
- чрезмерных скруглений;
- большого количества декоративных элементов;
- слишком большого количества разных цветов;
- нескольких competing accent colors;
- неочевидных icon-only действий без tooltip;
- визуальных эффектов, мешающих работе.

- по плотности информации;
- по предсказуемости;

Исправляй:

- visual hierarchy;
- navigation;
- spacing;
- typography;
- cards;
- tables;
- lists;
- buttons;

- forms;
- filters;
- tabs;
- statuses;

# 12. ЦВЕТА AGENT HUB

Пересмотри существующую цветовую систему.

Цвета должны быть:

- спокойными;
- современными;
- согласованными;
- комфортными для длительной работы;
- хорошо читаемыми.

Не используй большое количество насыщенных цветов.

Цвет должен прежде всего передавать смысл:

- success;
- warning;
- error;
- active;
- selected;
- disabled;
- informational state.

Если это можно сделать в рамках UI-слоя, приведи приложение к единой системе semantic design tokens:

- `background`;
- `surface`;
- `surface-elevated`;
- `border`;
- `text-primary`;
- `text-secondary`;
- `text-muted`;
- `accent`;
- `accent-hover`;
- `success`;
- `warning`;
- `danger`;
- `info`;
- `focus`.

Не добавляй десятки локальных случайных HEX-цветов в разные компоненты, если можно использовать общую систему.

# 13. DESIGN SYSTEM

Стремись к единой системе стилей для IDE и Agent Hub.

По возможности унифицируй:

- colors;
- spacing;
- typography;
- icon sizes;
- borders;
- radii;
- shadows;
- animation duration;
- z-index;
- controls;
- focus ring;
- interaction states.

Предпочитай:

- CSS variables;
- theme variables;
- semantic design tokens;
- shared primitives.

Избегай случайных значений вроде:

- `13px`;
- `17px`;
- `19px`;
- `7px`;
- `11px`;

если для них нет причины.

Не нужно насильно превращать каждое значение в token, но основные размеры должны иметь систему.

---

# 14. КОМПОНЕНТНАЯ АРХИТЕКТУРА

Следи за ответственностью компонентов.

Компонент не должен без необходимости одновременно:

- управлять сложным состоянием;
- содержать бизнес-логику;
- выполнять запросы;
- реализовывать сложный layout;
- содержать сотни строк визуальной разметки.

Разделяй код там, где это реально улучшает архитектуру.

Выноси переиспользуемые элементы, если это оправдано.

Например:

- ToolWindow;
- SidebarItem;
- ToolbarAction;
- EditorTab;
- PanelHeader;
- ResizablePanel;
- StatusBadge;
- Dropdown;
- ContextMenu;
- TerminalTab;
- EmptyState;
- ErrorState;
- common form controls.

Но **не создавай abstraction ради abstraction**.

Если элемент маленький, понятный и используется один раз, необязательно искусственно превращать его в отдельную систему.

---

# 15. STATE MANAGEMENT

Не добавляй глобальное состояние без необходимости.

Локальное UI-state должно оставаться локальным.

Глобальное/shared state используй только там, где оно действительно должно разделяться между несколькими частями приложения.

Например, IDE layout state может включать:

- открытые tool windows;
- положение панелей;
- размеры панелей;
- active bottom panel;
- panel visibility;
- toolbar configuration;
- layout preferences.

Такая модель должна быть централизованной, понятной и предсказуемой.

Не размазывай связанную layout-логику по десяткам независимых компонентов.

---

# 16. ПРОИЗВОДИТЕЛЬНОСТЬ

Не ухудшай производительность интерфейса ради красоты.

Обращай внимание на:

- лишние re-render;
- тяжёлые вычисления внутри render;
- ненужные listeners;
- утечки event handlers;
- layout thrashing;
- чрезмерные animations;
- повторные запросы;
- ненужное глобальное состояние;
- большие списки без virtualization, если она реально нужна.

Особенно внимательно проверяй:

- File Explorer;
- Git History;
- Logs;
- Terminal output;
- Agent lists;
- Task history;
- Database explorer;
- большие таблицы.

Не оптимизируй преждевременно всё подряд, но исправляй очевидные UI-performance проблемы.

---

# 17. ВИЗУАЛЬНЫЕ БАГИ — ВЫСОКИЙ ПРИОРИТЕТ

Во время каждого цикла активно ищи UI-баги.

Например:

- элементы выходят за границы;
- текст обрезается;
- неправильный overflow;
- layout ломается при resize;
- dropdown открывается под другим элементом;
- modal выходит за viewport;
- tooltip перекрывает важный UI;
- неправильный z-index;
- неправильные размеры sidebar;
- layout shifts;
- элементы смещаются после загрузки;
- одинаковые кнопки имеют разные размеры;
- inconsistent padding;
- плохое alignment;
- сломанные hover/focus/active states;
- плохой contrast;
- слишком маленькие clickable areas;
- ошибки при длинных названиях;
- проблемы при разных разрешениях;
- артефакты при открытии/закрытии панелей;
- неправильное поведение flex/grid;
- ненужные horizontal scrollbars;
- content clipping;
- overlapping elements.

Если исправление находится внутри UI-слоя — исправляй.

---

# 18. RESIZE И РАЗНЫЕ РАЗМЕРЫ ОКНА

Point — desktop-oriented приложение.

Не нужно превращать его в mobile-first web interface.

Но IDE и Agent Hub должны нормально работать при:

- широком мониторе;
- обычном desktop resolution;
- ноутбуке;
- уменьшенном окне;
- изменении размера окна;
- нескольких открытых панелях одновременно.

Не допускай разрушения layout при resize.

Проверяй разумные minimum widths/heights.

---

# 19. ACCESSIBILITY И INTERACTION QUALITY

Не нужно превращать задачу в отдельный accessibility rewrite, но базовые вещи должны быть сделаны правильно.

Проверяй:

- keyboard focus;
- focus visibility;
- tab navigation;
- click targets;
- contrast;
- disabled states;
- tooltip для непонятных icon-only actions;
- предсказуемость controls;
- правильную визуальную реакцию на interaction.

Не убирай focus outline без замены на нормальный focus state.

---

# 20. НЕ УХУДШАТЬ ФУНКЦИОНАЛЬНОСТЬ РАДИ КРАСОТЫ

Перед каждым значимым изменением задай себе вопросы:

1. Стало ли визуально лучше?
2. Стало ли понятнее?
3. Стало ли быстрее выполнять типичные действия?
4. Не исчезла ли полезная информация?
5. Не стало ли больше лишних кликов?
6. Не нарушена ли существующая функциональность?
7. Не затронуто ли ядро?
8. Не ухудшилась ли поддерживаемость кода?
9. Не создан ли новый технический долг?

Если изменение выглядит красивее, но ухудшает работу — не делай его.

# 21. ПОРЯДОК ПРИОРИТЕТОВ

1. Визуальные баги.
2. UX-проблемы, мешающие работе.
3. Непонятная навигация.
4. Layout и организация рабочего пространства.
5. Консистентность компонентов.
6. Архитектура UI-кода.
7. Цветовая система.
8. Typography.
9. Spacing.
10. Interaction states.
11. Micro-interactions.
12. Незначительные декоративные улучшения.

Не трать цикл на изменение пары оттенков, если существуют очевидные UX или layout-проблемы.

# 23. ПЕРЕД КАЖДЫМ ЦИКЛОМ

Перед изменениями:

1. Изучи существующую реализацию.
2. Осмотри изменяемые компоненты.
3. Пойми текущую архитектуру.
4. Определи реальные визуальные/UX проблемы.
5. Отдели UI-проблемы от проблем ядра.
6. Выбери небольшой логически связанный scope.
7. Продумай архитектурно правильную реализацию.
8. Только после этого вноси изменения.

Не меняй код только потому, что «можно сделать иначе».

Изменение должно иметь понятную причину.

---

# 24. ПРОВЕРКА ПОСЛЕ ИЗМЕНЕНИЙ

После каждого цикла запускай доступные проверки проекта:

- typecheck;
- lint;
- tests;
- build.

Если есть UI/e2e tests — запускай релевантные тесты изменённой области.

Если доступны visual regression tests — используй их.

Не отключай проверки ради успешной сборки.

Не используй как стандартное решение:

- `any`;
- `@ts-ignore`;
- eslint disable;
- пустые `catch`;
- подавление ошибок;
- временные production-заглушки.

Если существующая проблема мешает проверке и не относится к твоим изменениям — зафиксируй это в отчёте.

---

# 25. UI-АРХИТЕКТУРА VS ЯДРО

Если обнаруживается плохая архитектура существующего кода, разделяй её на две категории.

## UI-архитектура

Если проблема полностью внутри UI-слоя и её безопасное исправление необходимо для текущей задачи — можешь исправить.

Например:

- дублирование UI-компонентов;
- хаотичные цвета;
- плохой layout structure;
- повторяющиеся стили;
- монолитный visual component;
- неправильно организованное UI-state;
- отсутствующие shared primitives.

## Ядро / системная архитектура

Если изменение требует затронуть:

- backend;
- core;
- API contracts;
- runtime;
- agent orchestration;
- storage;
- protocol;
- domain logic;
- системную архитектуру Point;

**не исправляй.**

Только зафиксируй.

---

# 26. ФОРМАТ ОТЧЁТА ПОСЛЕ КАЖДОГО ЦИКЛА

После каждого цикла дай короткий структурированный отчёт.

## Изменено

Для каждого изменения:

- что было изменено;
- где;
- зачем;
- какой UX/UI эффект получен.

## Архитектура

Укажи:

- какие существующие abstractions использованы;
- были ли созданы новые UI primitives;
- почему выбранная реализация архитектурно корректна;
- не появилось ли unnecessary duplication.

## Проверено

Укажи:

- typecheck;
- lint;
- tests;
- build;
- ручные UI scenarios;
- размеры окна;
- состояния компонентов.

## Найденные визуальные проблемы

Перечисли проблемы, которые заметил, но пока не вошли в текущий cycle.

## Найденные проблемы ядра

Для каждой:

- location;
- description;
- reproduction;
- expected behavior;
- actual behavior;
- предполагаемая причина;
- severity.

Не исправляй эти проблемы.

## Следующий цикл

Коротко укажи наиболее логичное направление следующей итерации.

---

# 27. КРИТЕРИЙ КАЧЕСТВА КОДА

После каждого изменения оценивай не только то, как интерфейс выглядит сейчас, но и насколько легко будет:

- поддерживать этот код;
- расширять интерфейс;
- добавлять новые tool windows;
- добавлять toolbar actions;
- добавлять terminal types;
- добавлять Agent Hub sections;
- менять тему;
- менять layout;
- исправлять ошибки;
- тестировать компоненты;
- переиспользовать primitives.

Код должен выглядеть как часть долгосрочно развиваемого production-продукта.

Не оставляй после себя реализацию, которую придётся переписывать через несколько недель.

---

# 28. ГЛАВНЫЙ КРИТЕРИЙ РЕЗУЛЬТАТА

После серии итераций **Point IDE должна ощущаться как зрелый профессиональный инструмент уровня современных IDE**.

Нужная информация должна появляться тогда, когда она нужна.

Редко используемые функции не должны постоянно занимать экран.

JetBrains используется как референс по:

- структуре рабочего пространства;
- tool windows;
- терминалам;
- панелям;
- плотности UI;
- навигации;
- организации большого количества инструментов.

Не делай буквальную копию JetBrains.

Адаптируй эти принципы под архитектуру и задачи Point.

**Agent Hub должен ощущаться естественной частью того же продукта Point**:

- общая visual language;
- понятная навигация;
- хорошие цвета;
- высокая читаемость;
- предсказуемые interaction states;
- отсутствие визуальных дефектов.

Финальная формула:

**минимум визуального шума + максимум полезного пространства + нативно понятный UX + архитектурно чистый код + никакого вмешательства в ядро без отдельной задачи.**
