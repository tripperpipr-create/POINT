# Agent Hub v2 — MVP

14 сентября 2026. Этот документ сокращает полный план v2 до минимального
работающего контура. Полный контракт остаётся целью и перечислен в конце; здесь
зафиксировано только то, без чего контур «наряд → доказательство → доставка» не
работает честно.

Основание — проверка 14 сентября: `go build ./...`, Go-тесты
`domain/storage/app/httpapi`, `scripts/check-docs.mjs` и
`scripts/check-release-contracts.mjs` зелёные, но ни один критерий закрытия
полного плана не выполнен. Три блокера: профиль проверок существует только как
список имён и шлюзом не требуется; сертификация моделей никогда не даёт
`certified`, поэтому Auto недостижим; перезапуск ядра оставляет квест в ложном
`running`.

## Что обещает MVP

Один реальный сценарий проходит от первого сообщения Мастеру до работающего
приложения без вмешательства в runtime, и:

- `completed` выдаётся только когда каждая обязательная проверка профиля
  исполнена и записана командой с кодом возврата;
- доставка подтверждена распиской, а заявление «приложение запущено» опирается
  на факт, а не на политику наряда;
- перезапуск ядра или Docker не теряет квест и не показывает ложное выполнение;
- Мастер показывает URL и Start/Stop доставленного приложения.

Всё остальное из полного плана MVP не обещает и не имитирует.

## Что вырезано и почему

| Полный план | Решение MVP |
| --- | --- |
| Auto-маршрутизация и сертификация моделей | Только Fixed. Auto остаётся в дереве под тестами, но Мастер его не предлагает: пути к `certified` нет, и держать на нём релиз нельзя |
| Reservations на наряд и веху, калибровка Small/Medium/Large, расчёт параллельности | Отложено. В MVP бюджет остаётся утверждённым числом, расход сходится в ledger постфактум |
| Playwright, WCAG, dependency audit, secret scan, performance, screenshots | Вне профиля MVP. Профиль сокращается до проверок, которые действительно исполняются |
| Integration Agent, автоматический replan незапущенных этапов | Отложено. Параллельные ветки в MVP не обещаются |
| Windows tray-сервис, автоподъём с checkpoint | Отложено. В MVP перезапуск переводит квест в паузу, продолжение — одной кнопкой |
| Полный cutover на v2 по умолчанию | Сделан 14 сентября по решению владельца: ядро открывает `hub-v2.db` по умолчанию, `POINT_AGENT_HUB_V2=0` возвращает прежнюю базу. Legacy-БД остаётся на диске нетронутой |
| Три живых сценария × 3 прогона | Один сценарий × 2 прогона подряд |
| Improvement proposal после квеста, простой/профессиональный режимы | Отложено. Карточка запуска уже редактируема, этого для MVP достаточно |

## Работы по порядку

### 1. Команды проверок стали частью наряда — сделано

`CompletionProfile` больше не список имён: каждая проверка несёт собственную
команду и ожидаемый код возврата (`internal/domain/work_order_v2.go`). Проверка
`acceptance` — единственная без команды, её доказывают критерии приёмки; для
любой другой отсутствующая команда не проходит валидацию. Профиль входит в
дайджест утверждения, поэтому после подтверждения команду нельзя подменить.

`masterCompletionProfileV2` в `internal/app/master_work_orders_v2.go` предлагает
только исполнимое: команды сборки и тестов берутся из манифестов, которые
действительно есть в воркспейсе (`internal/environment/analyzer.go`), а
`service_start` и `health` добавляются, когда наряд обещает работающее
приложение. Остальные виды проверок остаются в словаре и добавляются человеком
в карточке — вместе с командой.

У greenfield-наряда манифестов ещё нет, поэтому предложить команды сборки и
тестов неоткуда: угадывать `composer install` против `npm ci` по категории стека
нечестно. В такой карточке профиль приходит из `acceptance` и, при обещанном
приложении, `service_start` с `health`; команды сборки и тестов человек
дописывает сам перед подтверждением. Для живого прогона MVP это обязательный
шаг.

Карточка запуска показывает профиль в сводке и даёт редактировать его JSON до
утверждения (`vscode-extension/ui/client/master-work-order-v2.js`).

### 2. Шлюз требует профиль — сделано

`WorkOrderEvidenceStatus` в `internal/domain/evidence_gate_v2.go` сверяет каждую
обязательную проверку с записью в bundle: нет записи или команда другая —
`blocked` с причиной; команда исполнена и провалилась — `blocked` без ошибки,
как и любой честный провал. Доказательства профиля лежат под отдельным ключом
`completion:<вид>`, поэтому проверка критерия не может сойти за проверку
профиля. Ручная доставка не может дойти до `completed` и остаётся делом
приёмщика, поэтому профиль там шлюз не требует.

Разделены два разных исхода: противоречие внутри доказательств (нет записи,
подменённая команда, чужой дайджест) — это недоверенные доказательства и ошибка,
а честный провал — `blocked` с сохранённым bundle. По той же причине обещанное,
но не поднявшееся приложение больше не отдаёт ошибку: раньше расписка всегда
копировала флаг из политики, ветка была мёртвой, а с честной распиской она стала
живой и откатывала транзакцию вместе с доказательством того, почему сервис не
встал.

### 3. Исполнитель профиля — сделано

`internal/app/completion_profile_v2.go` прогоняет команды профиля после переноса
результата и записывает вид, команду, код возврата, длительность и усечённый
redacted-вывод. Команды исполняются на хосте в каталоге доставки: именно там
лежит результат, который откроет пользователь, и там же работает Docker
Compose. Каждая команда ограничена 15 минутами — иначе зависший старт сервиса
держал бы квест в `applying` без результата и без причины. Командная строка
передаётся оболочке дословно: стандартное экранирование Go превращает кавычки в
`\"`, и на Windows утверждённая команда с кавычками выполнилась бы как другая.

`ServicesRunning` в расписке больше не копируется из политики: расписка вправе
заявить работающее приложение только если утверждённая проверка `service_start`
действительно его подняла (`internal/app/work_order_evidence_v2.go`).

Результат, не прошедший собственный профиль, остаётся в проекте: удалять часы
работы хуже, чем оставить их с честной пометкой. Поэтому квест уходит в
`blocked`, а в bundle прямо записано, какие проверки провалились.

### 4. Перезапуск не оставляет ложного «выполняется» — сделано

`internal/app/quest_recovery_v2.go` при старте ядра находит утверждённые квесты
v2 в состояниях `preflight`/`running`/`verifying`/`applying` — их исполнителя
больше нет — и переводит их в `paused` с причиной перезапуска; writer-lease
остаётся за квестом, продолжение делается кнопкой в карточке. Tool call с
неизвестным исходом автоматически не повторяется.

Попутно выяснилось, что headless-ядро вообще не вызывало `Startup`: retention
песочниц, описанный как работающий, в продукте не запускался ни разу. Вызов
добавлен в `cmd/server/main.go`.

### 5. Fixed-only и честная сертификация — сделано

Мастер собирает наряд только с `Mode: "fixed"`, а Auto без certified-роутера
отклоняется валидацией наряда. Probe в `internal/app/model_capability_probe.go`
перестал писать «1 из 9» при каждом прогоне: прогоны матрицы накапливаются до
трёх, неудачный прогон обнуляет набор, а статус честно остаётся `experimental` —
для `certified` нужна ещё известная стоимость и явное решение, и это работа
после MVP.

### 6. Внешний конфликт — это ручная приёмка — сделано

Конфликт внешнего изменения воркспейса помечается отдельным классом ошибки,
перенос откатывается целиком, и шлюз отдаёт `needs_review` вместо `blocked`:
работа проверена, её нужно принять руками
(`internal/app/work_order_evidence_v2.go`, `internal/domain/evidence_gate_v2.go`).

## Приёмка MVP

Гейты:

```powershell
go build ./...
go test ./internal/...
node scripts/check-docs.mjs
node scripts/check-release-contracts.mjs
node scripts/run-hub-smokes.mjs
```

Живой сценарий — один: Symfony + Docker Compose + PostgreSQL + endpoints + tests
+ README, на чистой Hub v2 БД (теперь она и есть база по умолчанию) и Fixed-модели, два
прогона подряд с одним стартовым approval и без вмешательства в runtime. Он
запускается харнессом:

```powershell
node scripts/run-v2-mvp-acceptance.mjs --run=1
```

Без переменных харнесс проверяет только правила вердикта — что именно считается
выполненным MVP — и выходит с нулём. Живой прогон включается
`POINT_V2_MVP_LIVE=1` вместе с `POINT_V2_MVP_MODEL`, базовым URL, ключом и
`POINT_SANDBOX_BACKEND=docker`; результат ложится строкой в
`.tmp/v2-mvp-<модель>-run<N>.jsonl` — статус, время, число вмешательств,
исполненные проверки, расписка и список нарушений. Отдельно помечается
false completion: квест сказал `completed`, а приёмка нашла нарушение.

Правила вердикта живут в `internal/acceptance/work_order_mvp_test.go` и
проверены на подделках — пропущенная проверка профиля, подменённая команда,
проваленная проверка, ненайденная расписка, недоказанные сервисы и пустой
ledger. Это сделано намеренно: приёмка, которую никто не исполняет, — ровно та
ошибка, которую MVP и чинит.

Что харнесс делает перед утверждением — это в точности шаги человека, а не
обход контура: настраивает подключение, профиль исполнителя и **политику
Мастера** (без неё разговор невозможен), открывает проект, из которого ведётся
разговор, отвечает Мастеру на уточняющие вопросы («решай разумными
умолчаниями») и дописывает в карточку команды сборки и тестов, которых у
greenfield-наряда взяться неоткуда. До 14 сентября (ночи) ничего этого не было:
сценарий падал на первом же ходе с «мастер не настроен», и живой прогон не
исполнялся ни разу.

Живой прогон можно вести и на локальном рантайме — `POINT_V2_MVP_PROVIDER=ollama`
с `POINT_OLLAMA_BASE_URL` (по умолчанию `http://127.0.0.1:11434`), ключ там не
нужен. Практический предел честно замерен: на CPU-инференсе 9B-модели выходит
~6 токенов/с, один ход Мастера — 2,5 минуты, шаг агента — 3–8 минут, и сценарий
Symfony + Compose + PostgreSQL не укладывается ни в `activeSeconds`, ни в
`maxSteps` наряда. Для закрытия MVP нужен быстрый endpoint; локальная Ollama
годится для проверки самого контура, а не для приёмки.

Fault-набор MVP: timeout или rate limit исполнителя, перезапуск ядра в середине
работы, внешнее изменение файла в workspace.

MVP закрыт, когда оба прогона дали `completed` с полным профилем и распиской, ни
один прогон не завершился ложно, приложение после доставки отвечает по URL, а
Start/Stop из карточки работают. Живой прогон — единственное, что осталось:
работы 1–6 закрыты и покрыты тестами, включая сквозной прогон настоящего
терминального пути (утверждение → колбэк Flow → доставка → профиль → расписка →
шлюз) в `internal/app/completion_delivery_v2_test.go`.

**Полигон рядом — не замена этой приёмке (19 сентября).** `make loop`
(`internal/acceptance/live_loop_test.go`) гоняет лёгкую задачу в настоящем
проекте: эндпоинт с тестом, круг полминуты. Он идёт по полосе «Агент»
(`StartFastAgent`), где квест заводится сразу активным с одним ручным критерием
и **шлюза доказательств нет вовсе**, — то есть проверяет работу агента, а не
контур завершения. Путать их нельзя: лёгкая задача едет мимо шлюза, и ни один
её прогон не говорит ничего о том, сойдутся ли шестнадцать условий здесь.

Смысл полигона — цена круга. Пока единственная живая проверка стоила часов,
дефект не успевал быть найденным дважды; на полминуты его можно найти, починить
и проверить. Три первых круга вскрыли три отказа, из них два в ядре —
непрозрачный ответ при отсутствии исполнителя и треть шагов, сгоравшая на
формате аргументов инструмента. Оба чинились бы вслепую по журналам этой
приёмки. Записи — в [PROJECT-STATUS.md](PROJECT-STATUS.md).

## Остаётся после MVP

Auto-маршрутизация и путь к `certified`; reservations на наряд и веху; калибровка
пресетов бюджета и расчёт параллельности по ресурсам; Integration Agent и
автоматический replan; tray-сервис, автоподъём с checkpoint и системные
уведомления; Playwright, WCAG, dependency audit, secret scan, performance и
screenshots в профиле; improvement proposal после квеста; простой и
профессиональный режимы; сценарии среднего ТЗ и crypto analyzer вместе с полным
fault-набором. Legacy-поверхности (Agents, Quests, Flow, Change Set) в интерфейсе
пока остаются: переключена база, а не набор экранов.
