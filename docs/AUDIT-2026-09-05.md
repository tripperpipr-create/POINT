## Дефекты и доработки

### A01. Критичный: защита «SQL только для чтения» допускает изменение данных

Источники: [classify.go](../internal/dbconn/classify.go), [query.go](../internal/dbconn/query.go), [open.go](../internal/dbconn/open.go), [db_connections.go](../internal/app/db_connections.go), [sql_tools.go](../internal/tools/sql_tools.go).

`containsMutatingCTE` ищет ключевые слова только с обычными пробелами по краям. Перевод строки перед DELETE обходится без обнаружения записи. EXPLAIN целиком объявлен читающим. `RunQuery` затем доверяет классификатору и вызывает `QueryContext`, который сам по себе не запрещает мутации.

Воспроизведение на временной БД с одной строкой:

```sql
WITH x AS (SELECT 1)
DELETE FROM audit_items RETURNING id
```

Фактический вывод диагностического запуска:

```text
classification = read
RunQuery AllowWrite=false: kind=read error=<nil> returned=1 remaining=0
```

Также `EXPLAIN ANALYZE DELETE FROM audit_items` классифицируется как `read`.

Дополнительная граница: `OpenConfig.ReadOnly` реально применяется только к SQLite (`mode=ro`). В ветках PostgreSQL и MySQL этот флаг не применяется. Поэтому в удалённых БД с правами на запись классификатор не подкреплён серверным read-only ограничением. И HTTP use case, и `db_query` пользуются этим классификатором.

Важно о доказательстве: удаление воспроизведено на уровне реального `RunQuery` с writable SQLite в памяти. Сквозное выполнение через HTTP на PostgreSQL/MySQL не запускалось. Обычная файловая SQLite, открытая приложением через `mode=ro`, имеет дополнительную защиту; не следует переносить результат на неё без этой оговорки.

Исправление: серверно обеспеченный read-only режим/транзакция для читающих запросов, fail-closed разбор SQL, проверки CTE с разными пробельными символами, EXPLAIN ANALYZE и вызывающих функции SELECT. Одного расширения списка подстрок недостаточно. До исправления обещание в docs/databases.md «нет тихого destructive SQL» нельзя считать доказанным.

### A02. Высокий: диагностический frontend теряет несохранённый текст

Источник: [App.tsx](../frontend/src/App.tsx), строки 69–100.

Два независимых сценария:

1. Ввести текст, сохранить, продолжить печатать до завершения API-запроса. Ответ вызывает `setDraft(next.content)` и заменяет более свежий черновик содержимым отправленного ранее сохранения. Воспроизведено на извлечённом из исходника обработчике с управляемым Promise: ожидался `new typing while save is pending`, получен `submitted`.
2. Ввести текст и переключить проект через `chooseWorkspace` или `openRecent`. В отличие от `openFile`, эти обработчики не проверяют `dirty`, но обнуляют файл и черновик. Подтверждено анализом прямого пути кода; Wails UI вручную не запускался.

Исправление: привязать ответ сохранения к документу и его ревизии, сохранять новые правки в draft, защищать переключение проекта тем же договором несохранённых изменений. Для асинхронных открытий также нужен контроль актуальности ответа.

Область: Wails/Docker диагностический клиент; это не доказательство потери текста в нативном редакторе Code-OSS.

### A03. Высокий: clean CI не собирает core до обязательных Hub smoke

Источники: [.github/workflows/ci.yml](../.github/workflows/ci.yml), [.github/workflows/production-release.yml](../.github/workflows/production-release.yml), [run-hub-smokes.mjs](../scripts/run-hub-smokes.mjs), [core-binary.js](../scripts/lib/core-binary.js), [.gitignore](../.gitignore).

`npm run check` вызывает Hub suite; два его smoke запускают `point-core`. `vscode-extension/bin/` игнорируется Git. В extension job обычного CI нет предварительной сборки Go-бинарника. Production workflow также вызывает extension check до своей сборки Code-OSS/core. Job с Go-тестами не передаёт core артефактом в extension job.

Следствие для clean checkout: обязательный тест потребует отсутствующий binary. Если binary случайно сохранился на self-hosted runner, возможен отказ из-за его возраста. Это вывод из workflow и зависимости тестов; GitHub runner в этом аудите не запускался.

Исправление: явно собирать core из того же checkout перед Node checks либо передавать точно атрибутированный артефакт. Зелёный check-release-contracts не обнаруживает эту ошибку порядка выполнения.

### A04. Средний: проверка навигации сломалась после декомпозиции

Источники: [check-point-navigation.mjs](../scripts/check-point-navigation.mjs), строки 6, 12, 191–192; [ide-action-controller.js](../vscode-extension/ide-action-controller.js), строки 21–37.

### A06. Средний: Docker UI предлагает недоступный выбор проекта

Источники: [api.ts](../frontend/src/api.ts), строка 37; [App.tsx](../frontend/src/App.tsx), строки 129, 146, 160.

## Границы аудита

Полный исходный Git baseline недоступен. Race detector не запускался: CGO_ENABLED=0, gcc в PATH не найден. Не проверялись все живые комбинации моделей/провайдеров, внешние PostgreSQL/MySQL/SSH, Docker controlled-egress integration, новый Electron visual/E2E, installer lifecycle, performance/8h/24h/field/dogfood, текущие сетевые CVE. Smoke с моделью используют тестовый provider и подтверждают контракт приложения, а не качество конкретной внешней модели.

Аудит не доказывает отсутствие других ошибок и не выдаёт исторические evidence за свежую приёмку. Основной положительный результат — текущие Go-исходники собираются и проходят полный test/vet, а отдельный свежий core проходит сквозной путь разговора, создания агента/отряда и запуска квеста с подтверждениями. Основной отрицательный результат — зелёные существующие gates пропускают воспроизведённые SQL/save дефекты и не гарантируют актуальность поставки.
