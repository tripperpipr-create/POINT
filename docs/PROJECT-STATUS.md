Позднейший прогон этой Go-задачи 25 сентября выявил дефект резервного Flow: при отсутствии `composer.json` подготовка завершалась без действий, а PHP-ориентированный контракт реализации запрещал `go.mod`, `Dockerfile`, `.dockerignore`, Compose и файлы вне `src/config/public`. Реализация дошла до предела 24 шагов, затем её изменения были отвергнуты на `.dockerignore`. По уточнённому решению резервный Flow при ошибке планировщика убран: Point повторяет запрос модели один раз, после второго отказа сообщает ошибку и не запускает исполнителей. Для проектного задания без настроенного планировщика нужен явно выбранный Flow. `go test ./... -count=1`, узкие тесты планировщика и документационный затвор прошли; `go vet` остаётся красным на недостижимом коде в `agent_selector_lifecycle_test.go`, staticcheck — на восьми неиспользуемых функциях вне этой правки. 26 сентября разобраны два живых квеста на llmux (Qwen3.8-27B) в проекте `systemio`: «Go-сервис с /health, PostgreSQL и docker compose» (`blocked`) и последовавшая правка «заменить самописный протокол на pgx» («готово с ограничениями»). Найденные причины и что изменено:

- **Сеть задания.** Хосты реестров добавлялись только для Symfony. Go-заданию досталась одна `docker.io`, и планировщик велел исполнителю «use only the Go standard library» — так появился рукописный протокол PostgreSQL с ошибкой в порядке байтов. Теперь реестры языка из задания или манифеста попадают в карточку сами (`masterNetworkGrantsV2`, `environment.RegistryHosts`).
- **Планировщик.** Он получает `executionEnvironment`: Docker в песочнице, хосты, критерии, которые проверяет хост. План отклоняется, если стадия поручает исполнителю Docker там, где его нет, или ограничивает его стандартной библиотекой без решения человека. Причина отказа передаётся во вторую попытку.
- **Навыки Мастера.** Драйвер — отдельное решение с де-факто стандартной библиотекой. Поправка человека становится предложением памяти.
- **Проверки на хосте.** Добавлены поля JSON (`expectJson`) и сценарий сбоя зависимости с восстановлением: «база упала» больше не ручной критерий. Занятый порт называет владельца. Итог называет проваленный критерий, а не «acceptance, acceptance».
- **Самообучение.**
  - `fmt.Sprint(nil)` = `"<nil>"` делало все выученные навыки одним семейством, и откат регрессного навыка был запрещён — канарейка заклинила (21 раз в журнале). Исправлено, цикл оценки больше не обрывается на первой ошибке.
  - Сбой ревизует навык восстановления своей категории вместо нового, у агента не больше пяти выученных навыков.
  - Навык проекта без базы доказывается тремя чистыми квестами.
  - Бюджет обучения Мастера не ограничивает бесплатный рантайм, свежие задания обучения идут раньше отложенных.
- **Память.** Предложение памяти показывается под ответом, который его сделал.

26 сентября, волна 1 плана доводки («цикл не застревает и не врёт»):

- **Старт без Docker.** Раньше ядро не запускалось вовсе — 11 раз «configure execution sandbox» в журналах, и вместе с ним пропадали чат и IDE. Теперь `ContainerBackend` откладывает проверку демона: песочница честно отказывает «Docker недоступен — запустите Docker Desktop», сама перепроверяет демон не чаще раза в 15 с, а причина видна в Хабе. На хост ничего не переходит.
- **Карантин задания.** Подпись утверждения — `sha256` от JSON задания, поэтому любое изменение схемы делало старые записи недействительными. Одна такая запись роняла `/api/bootstrap`, сессии и восстановление. Теперь запись читается, её квест может менять статус, но не исполняется, пока задание не утвердят заново. Изменённое задание по-прежнему проходит полную проверку.
- **Ручная приёмка критерия.**
  - Ручной критерий без решения человека даёт `needs_review`, а не «готово с ограничениями». Это закрывает открытое решение из раздела ниже.
  - Решение (`accepted` или `rejected`) записывается в неизменяемую таблицу `work_order_manual_reviews_v2` через `POST /api/v2/master/quests/{id}/criteria/{criterionId}/review` и кнопки «Принято / Не принято» в карточке. Шлюз пересчитывает статус поверх неизменяемых доказательств.
- **Остановка ядра посреди запуска.** Запуск, прерванный остановкой ядра, больше не становится «blocked · context canceled»: квест встаёт на паузу с причиной «Ядро перезапустилось». Если исполнять ещё было нечего, расширение продолжает его само, с ключом из SecretStorage. Каждая остановка ядра пишет в журнал, откуда она пришла.
- **Отказ при отклонении набора правок** называет выход: остановить зависимое исполнение или отменить его квест.

Остальные тупики из журнала 21–23.09 (удаление квеста и агента, пауза на паузе, утверждение без субагента) после 24.09 не повторялись — их закрыл каскадный снос `PurgeQuest`.

Из волны 2 сделано: исполнитель на бесплатном рантайме получает окно модели вместо исторических 32768 (меняется только снимок прогона, профиль не трогается), а `run_command` называет реальную оболочку (в песочнице — busybox `sh`, не bash). Этап bootstrap с `composer.json` Go-проектам больше не встречается: он жил только в резервном Flow, убранном 25.09. Ещё не сделано: предел шагов по роли этапа, сокращение этапов `EnsureProjectPipeline`, отдельный проверяющий.

Проверено тестами исходников и смоуками вебвью (Node 23). Выложено в `.cache\VSCode-win32-x64` и установленное приложение, SHA-256 ядра совпадает. Живая приёмка ещё не выполнялась.

Известный плавающий тест: на Windows тесты Мастера в `internal/app` изредка падают на очистке `TempDir`, потому что `hub-v2.db` ещё занята. На исходном `master` воспроизводится так же (`TestMasterRefusesToProposeWithAnIncapableParty`), к этим правкам не относится.

Ближайший затвор: повторить от первого сообщения до доставленной ревизии и независимых проверок короткую и среднюю задачу; после этого сверить фактические режимы изоляции, восстановление после перезапуска и причины `blocked` с UI и справочниками. Параллельная оркестрация и самообучение не расширяют обещание продукта, пока этот затвор не пройден.

Открытое решение для целевой модели: текущий evidence gate допускает `completed` с `partial` assurance при ручном критерии или недоступной проверке. Цель в [PRODUCT-VISION.md](PRODUCT-VISION.md) требует отдельной ручной приёмки обязательного ручного критерия. До изменения контракта UI должен явно показывать неполную уверенность, а `completed` нельзя трактовать как полностью проверенный результат.
