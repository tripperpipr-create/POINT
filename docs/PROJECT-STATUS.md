## Скорость Мастера: первый этап — кандидат исходников, 2026-10-04

Ожидаемое поведение, границы и воспроизводимый benchmark зафиксированы в [master-performance.md](master-performance.md). Кеш используется закреплённым workspace v2 и старым путём; ключ включает поколение индекса, 16 записей LRU и TTL 30 секунд, общая подготовка отменяется только при уходе последнего ожидающего. Git-история принимает отдельный `revision`, проверенный локально до SHA. Измерения подготовки, полного хода, отдельных попыток модели и интервалов чтения добавлены в существующий `detail` без миграции БД и новых маршрутов. Отчёт группирует точные данные по workspace/turnId и отдельно показывает приблизительную историю.

Профильные регрессии и benchmark прошли. Медиана подготовки на синтетическом проекте 10 000 файлов: холодный кеш 33,88 мс, повтор 0,00240 мс, после обновления индекса 14,38 мс; сборка индекса вне этих измерений. Проверено на текущем дереве:

- остальные 39 шагов extension: свежая сборка ядра, UI/runtime, контракты инструментов/интерфейса и Хаб 88/88;
- совместимость отчёта с существующей БД Point в режиме только чтения: старая история показана отдельно как приблизительная;
- контрольный benchmark без параллельных проверок: 10 операций × 3 запуска, исходный вывод — build/master-performance-20261004.txt.

## Единое пространство Git — кандидат исходников, 2026-10-03

Ожидаемое поведение и границы зафиксированы в [Git workspace](git-workspace.md). Ручной коммит берёт настоящий index; коммит задачи сохраняет подготовленные пользовательские blobs и ограничен файлами задачи. Локальные операции используют общий исполнитель и блокировку репозитория. Workspace и repository передаются явно; GitLab получает отдельные connection/project.

Добавлены общая панель и вкладка Git, история с parent-графом, частичная подготовка, ветки/tags/remotes/stash, конфликты и продолжение/отмена операций. GitLab REST использует общий контракт провайдера: несколько аккаунтов, очередь MR, создание/редактирование, комментарии редактора, ответы/разрешение, approve/merge, CI и повтор. AI возвращает предложения с исходной ревизией; применение и публикация остаются действиями пользователя. Старые входы и API сохранены адаптерами, secretRef мигрирует без копирования токена в настройки.

Проверено на исходниках:

Полные затворы extension/docs остаются красными на пяти ранее существовавших пунктах check-release-contracts: дрейф Dockerfile, integration test и provenance, отсутствующая атрибуция пакета Python. Аттестации sandbox эта задача не изменяет. Остальные проверки этих контуров пройдены отдельно: сборка core/UI/runtime, контракты и статические проверки webview, профильные smoke-тесты, Хаб 88/88. Проверка документации и quality gate проходят.

## Поиск по тексту не съедает ход Мастера — 2026-10-02

**Индекс видит код команды, а не тома Docker.** Замер на `cf-bitrix` показал: индекс держал 511 файлов, из них 492 из `docker/` и ни одного из `source/` — предел в 200 тысяч записей уходил на тома раньше, чем обход доходил до кода. Теперь индекс, его проверка на расхождения, точечное обновление и поиск без git соблюдают `.gitignore` на каждом уровне, `.git/info/exclude` и свой `.pointignore` (разбор свой, git не нужен). Папки данных СУБД узнаются по маркерам (`ibdata1`, `PG_VERSION` и т. п.). При упоре в предел первыми индексируются файлы, которые команда меняет (число правок в последних 2000 коммитах, без git — время изменения). Результат на `cf-bitrix`: 16 306 файлов, `source/local` (компоненты и модули команды) в индексе, `docker/` — нет. Ядро Битрикса по-прежнему не помещается целиком в 256 МБ; исключить его можно строкой в `.pointignore`.

Вопрос «/api/documents — как работает этот метод?» в `cf-bitrix` думал 15 минут и упал с «Модель Мастера не ответила». Причина: `search_text` 925 секунд читал 343 тысячи файлов (в `docker/` 14,6 ГБ томов и логов). Срок хода кончился, и даже ответ «по собранному» ушёл уже на истёкшем контексте.

Исправлено:
- **Поиск как у ripgrep** (`internal/workspace/search.go`). В репозитории подстроку находит `git grep -l -I --untracked` с учётом `.gitignore`, остальное (регулярки, кириллица без учёта регистра) — по `git ls-files -co --exclude-standard`. Двоичное пропускается. Проверка ссылок на выход из проекта — раз на папку, а не полный `Resolve` на файл (~27 мс на Windows).
- **Свой срок поиска** — 30 с. По его истечении возвращается найденное с `truncated`. Если ничего не найдено — отказ `search_timeout` с подсказкой сузить `path`/`glob`, а не пустое «нет».
- **Свой срок каждого читающего инструмента в ходе Мастера** — до 90 с и никогда не из запаса под последний круг модели (3 мин или самый долгий круг хода). Если ход всё же упёрся в срок, сообщение говорит об этом, а не «проверьте модель».

Замер на `cf-bitrix`: полный поиск подстроки — 8–9 с вместо 15 минут. Строки `/api/documents` в отслеживаемых и новых файлах проекта нет, и Мастер теперь может сказать это сразу. Проверено: тесты `workspace`, `tools`, `orchestrator`, `agent`, `companion`, `httpapi`, `app`, `go vet`, `staticcheck`. Живой ход Мастера после правки не повторялся.

## Git-агент: ветка до работы, коммит после успеха, отправка по решению — 2026-10-02

Сделано (исходники, без живого квеста):

- **Ветка в наряде** (`work_order.git`). Осмотр с `fetch --prune` без окон входа: удалена ли ветка на сервере, влита ли в основную, отстаёт ли; защиту даёт GitLab, если `origin` ведёт на подключённый, иначе имя ветки. От защищённой ветки агент предлагает новую, про незащищённую запуск ждёт выбора человека. Переключение — `git switch --no-track -c` при утверждении, до первого снимка песочницы. Ветка проверяется перед каждым запуском, пустые ветки после квеста убираются.
- **Коммит** — после сохранённого вердикта «выполнен» с проверенным итогом, только файлы квеста, автор — git-пользователь, служебные строки `Point-Quest`/`Point-Evidence`. При провале файлы остаются без коммита, кнопка «Откатить» проверяет все наборы до отката. Повторы и ожидание коммитов больше не плодят.
- **Отправка и MR** — только по кнопке карточки или карточке в чате. MR создаётся push-опциями GitLab; если GitLab его не создал, открывается страница «новый MR». Все действия пишутся в журнал `quest_git_actions_v2` (только дописывается).
- **Настройка** `localAgent.questGit`: `auto` (коммит сам, в конце вопрос об отправке) или `onRequest` (ничего без просьбы).
- **Ручная приёмка убрана** для заданий, меняющих проект: `propose_brief` отклоняет `manual`, навык критериев требует проверок, которые выполняет сам квест. Старые квесты в приёмке доживают.
- **Режим «План»** больше не предлагает ветку сам. Ручная кнопка берёт основу из осмотра git-агента (с сервера, а не отставшую локальную).

Anthropic получает метки `cache_control`; попадание в кэш (`cachedInputTokens`) пишется в `model.usage` у Anthropic и OpenAI-совместимых.
- **Кэши квеста.** Кэши npm, модулей Go, сборки Go и pip живут в томах Docker на квест, а не в tmpfs одной команды. Замер `go build` Point в песочнице: 63 с холодным кэшем, 10 с тёплым. Приёмка получает только кэши, сверяемые с lock-файлом.
- **Лишние вызовы Docker.** Дайджест образа проверяется один раз, а не перед каждой командой; `docker rm --force` после обычного завершения `docker run --rm` не зовётся; удачные пробы команд и версий образа не повторяются на каждом этапе. Время аудита рабочей папки вокруг команды пишется в `tool.finished` (`timing`).

1 октября, сервис проверок (`POINT_VERIFY_SERVICE=off|shadow|on`, по умолчанию `shadow`) — тесты исходников, живой приёмки нет:

- **Проверка перед приёмкой.** Пишущий этап несёт один ручной критерий `stage-complete` и о проваленной приёмке узнавал после неё. Теперь, когда последний пишущий этап перед Accept собрался завершиться, Point сам гоняет критерии приёмки в чистой копии его песочницы и при провале возвращает агенту причину — до двух раз, дальше судит приёмка. Заданию такого этапа сказано не гонять полные приёмочные команды самому.
- **Переиспользование.** Исход прогона хранится в неизменяемой `verification_results_v2` под ключом из отпечатка дерева, образа, исполненных команд и сети. В режиме `on` приёмка не гоняет заново целиком прошедший прогон с тем же ключом; доказательство называет исходный прогон, затвор доказательств отвергает ссылку без записи или с другим деревом. Провал не переиспользуется. В `shadow` приёмка гоняет всё сама и пишет, совпал бы взятый исход, — по этим записям режим `on` включается после живых квестов.
- Приёмка и проверка гоняют критерии одним кодом (`internal/app/criteria_batch.go`).
- Карточка наряда показывает исход последней проверки: «Проверки Point перед приёмкой: N из M прошли». Цена контрольных точек прогона (число, мс, байты) пишется в `model.requested` и видна в `point-perf-report`.

Не проверено вживую: доля попаданий в кэш на llmux (бэкенд неизвестен), выигрыш на целом квесте, совпадение исходов в `shadow`. Следующая фаза плана: рабочая копия песочницы в томе Docker с тёплым контейнером на этап (замер: `npm ci` 40 → 9 с, сборка в 3–5 раз быстрее, чем на bind mount из Windows). Отложено решением владельца: пропуск Integrate в последовательной цепочке, параллельные писатели, быстрая модель для ревью, параллельные чтения, поиск агентов-исследователей.
