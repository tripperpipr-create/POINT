# Point IDE — состояние проекта

Обновлено 13 сентября 2026 года, Point 1.2.2. Проект предназначен исключительно для личного использования. Критерий готовности — рабочие ежедневные сценарии, сохранность данных и согласованная локальная сборка.

**API-only (14 сентября).** Помощник и агенты принимают только HTTP-провайдеры
(Ollama / OpenAI-compatible / Anthropic / Azure). Claude Code, Codex и Cursor CLI
сняты из каталога и UI. Legacy-контур quest-proposals/flows в API сохранён, но
основной UI ведёт через WorkOrder v2 и Мастера.

## Контур v2: наряд → доказательство → доставка (11–13 сентября)

Единицей работы стал **WorkOrder** — неизменяемая карточка запуска, которую Мастер собирает, а человек утверждает целиком: цель, scope и out-of-scope, критерии приёмки, вехи, план воркспейса (`existing|managed`, изоляция `git_worktree|snapshot|live_write`), ростер, политика маршрутизации моделей, сетевые гранты, секреты, бюджет и политика доставки. Модель может только предложить черновик; утверждение, изоляция и маршрутизация выводятся из доверенного локального состояния. Меняющееся состояние исполнения вынесено в производный `runtime` и в дайджест утверждения не входит, поэтому ход квеста не меняет утверждённый договор.

Завершение больше не следует из успеха Flow. Единственный терминальный путь утверждённого наряда проходит через шлюз доказательств: `EvidenceBundle` версии 3 обязан совпасть по дайджесту наряда и по дайджесту снимков источников, нести окружение, версионированный stack-preset и исполненную запись на каждую утверждённую проверку профиля завершения. Структурное расхождение даёт `blocked`, а не `completed`. Доставка подтверждается `DeliveryReceipt`; при `commitMode=squash` создаётся ровно один commit по явному списку изменённых файлов, без `git add -A`. При `applyMode=manual` проверенный результат остаётся в `isolated_review` и намеренно не трогает воркспейс.

Сопутствующее: неизменяемые снимки источников (текст, PNG/JPEG/WebP, файл, публичный HTTPS, git) с refresh и ограниченным diff требований; сертификация моделей и credential-free манифест возможностей подключения; долговременная writer-lease на воркспейс, переживающая паузу и перезапуск процесса; retention песочниц квеста (закрытие старше 30 дней при старте ядра); управление доставленным Docker Compose приложением с проверкой версии, дайджеста, расписки и ключа идемпотентности.

Контракт описан в [api.md](api.md) (18 эндпоинтов `/api/v2/*`), модель — в [agent-hub-mvp.md](agent-hub-mvp.md), поток — в [architecture.md](architecture.md). Legacy-контур (`/api/quest-proposals/decide`, `/api/change-sets/*`, `/api/workflows/*`, `/api/flows/*`) сохранён рядом как совместимость; v2-колбэк Flow не может уйти по старому пути завершения.

## Разобран живой отказ запуска (14 сентября, ночь)

Первый живой прогон наряда встал: карточка навсегда показывала «Проверяем
окружение», кнопок, кроме «Отменить», не было, а созданного исполнителя человек
на карточке не видел. По журналу ядра и базе восстановлена вся цепочка:
утверждение в 22:19 упало на отсутствии Docker sandbox, три нажатия «Повторить
запуск» в 22:31 вернули наряд в `preflight`, после включения песочницы запуск
дошёл до планировщика milestone — и был оборван собственным таймаутом вебвью
(20 с) на 20-й секунде запроса к модели. Отменённый контекст унёс с собой и
запись отказа: квест остался в `preflight`, из которого нет выхода.

Закрыто:

1. **Запуск утверждённого наряда больше не живёт внутри HTTP-запроса.**
   `resumeApprovedWorkOrderV2` только начинает работу, а исход — `running`,
   `awaiting_user` или `blocked` с причиной — пишет фоновая задача со своим
   сроком (30 мин) и контекстом без отмены. Повторное нажатие не плодит вторую
   попытку: запуск один на квест, и «Отменить»/«Пауза» его останавливают
   (`internal/app/work_order_execution_v2.go`, `quest_controls_v2.go`).
2. **Карточка следит за живым квестом.** Пока её обновлял только ответ на
   нажатие, состояние замирало на снимке — независимо от того, что делал квест.
   Новый `vscode-extension/master-work-order-watch.js` опрашивает наряд, пока
   состояние переходное, и гаснет сам на исходе; обновление чужого разговора
   вебвью отбрасывает.
3. **«Будет создан» после утверждения стало «создан».** Исполнители создаются
   транзакцией утверждения, но карточка продолжала обещать их создание —
   человек искал создание агента, которого ядро уже создало. `WorkOrderRuntime`
   несёт `agentIds`, карточка сверяет ростер с ними.
4. **Включённый Docker sandbox перестал быть ловушкой.** Настройка глобальная, а
   ядро с `POINT_SANDBOX_BACKEND=docker` не стартует, пока Docker Engine не
   отвечает: IDE осталась бы без ядра во всех окнах. Теперь при таком отказе
   Point называет причину и предлагает выключить песочницу с перезапуском ядра.

## Проверено 14 сентября (ночь) — сквозной прогон гейтов и четыре закрытых дефекта

Пройдено без исключений: `go build ./...`, `go vet ./...`, `go test ./...` (38 пакетов),
`check-docs`, `check-release-contracts`, `run-hub-smokes` 56/56, полный
`npm run check` расширения, сборка frontend (`npm test && tsc && vite build`),
`check-quality-gate`, `check-point-navigation --source-only`, `check-shell-tokens`,
`check-shell-scales`. Race detector по-прежнему не запускался: нет gcc в PATH.

Найдено и закрыто с регрессионными тестами:

1. **Выдуманный `proposalId` ронял ход Мастера.** Поле приходит от модели, и на
   пустом проекте слабая модель заполняет его наугад; ход падал с «задание для
   обсуждения не найдено в этом проекте», унося весь разбор. Теперь ссылка от
   модели, которая никуда не ведёт, игнорируется, а та же ссылка от клиента
   остаётся ошибкой: человек указал карточку, которой здесь нет
   (`internal/orchestrator/task_intake.go`).
2. **Гашение «размышления» уходило на строгий endpoint.** `chat_template_kwargs`
   — поле сверх спецификации OpenAI; официальный API отвечает на него 400. При
   этом аварийный повтор ставил признак до конца прогона, то есть один ход,
   потративший вывод на размышление, отравлял ошибкой формата все последующие
   запросы. Правило вынесено в `domain.RuntimeAcceptsThinkingSwitch` (свой
   рантайм по пресету либо нативная Ollama) и применяется всеми тремя
   вызывающими: движком агента, Мастером и помощником.
3. **Squash-доставка ломалась в подпапке репозитория.** `git status --porcelain`
   печатает пути от корня репозитория, а список доставки — от папки проекта;
   открытый монорепозиторий получал «изменение вне утверждённой доставки» на
   собственных файлах. Добавлена поправка на `rev-parse --show-prefix`
   (`internal/app/work_order_git_delivery_v2.go`).
4. **`point-db verify` мог назвать повреждённую базу здоровой.** Обход
   `PRAGMA foreign_key_check` не проверял `rows.Err()`, поэтому оборванное
   чтение выглядело как «нарушений нет» (`internal/storage/maintenance.go`).

Отдельно приведён в рабочее состояние харнесс живой приёмки МВП: он ни разу не
исполнялся и падал на собственной обвязке — не настроен Мастер, не открыт
проект, карточка с открытыми вопросами не утверждается. Теперь сценарий
доходит до исполнения, отвечает Мастеру на уточнения и умеет работать на
локальном рантайме (`POINT_V2_MVP_PROVIDER=ollama`, ключ не нужен). Живой
результат по-прежнему 0/2: на CPU-инференсе локальной 9B (замер — 6,3 токена/с)
сценарий Symfony + Compose + PostgreSQL не укладывается в бюджет наряда, и
прогон нужно вести на быстром endpoint'е.
