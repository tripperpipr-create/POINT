# Point IDE — состояние проекта

## Текущий срез — 23 сентября 2026

Исходники core, frontend и расширения объявляют версию `1.2.3`. Цель продукта и порядок развития — в [PRODUCT-VISION.md](PRODUCT-VISION.md). Датированные проверки и решения сохранены отдельно в [журнале разработки](PROJECT-HISTORY.md).

В текущем дереве быстрый Agent на базе v2 создаёт WorkOrder и отдельный execution workspace (`internal/app/fast_agent.go`); завершение WorkOrder проходит через общий `EvidenceBundle` и gate (`internal/app/work_order_evidence_v2.go`). Legacy путь остаётся только при явном выборе старой базы. Более раннее описание прямой записи в историческом журнале относится к прежней реализации.

Подтверждённые живые результаты пока остаются прежними: несколько успешных прогонов небольшой Go-задачи и отсутствие двух последовательных PASS сложного PHP/URL-intake сценария. Текущий срез включает новые маршруты восстановления, обучения Мастера и UI; исходники и тесты прошли перечисленные далее проверки, но эти возможности ещё не прошли новую живую приёмку пользователя.

Проверено 23 сентября на текущем дереве: `go test ./... -count=1` — PASS; `npm --prefix vscode-extension run check` с Node 24 — PASS, в том числе 68/68 Hub smoke; `node scripts/check-docs.mjs` — PASS (210 API-маршрутов); `node scripts/check-release-contracts.mjs` — PASS. `TestDockerSandboxIntegration` с локальным release-образом — PASS, включая границы UID/GID, отсутствие прямого egress и разрешённый TLS через gateway. Реальный модельный прогон короткой или средней задачи в этот день не выполнялся.

25 сентября на ветке `feat/master-text-tools` Мастер перестал отвечать JSON-конвертом. Ответ — обычный текст, а задание, уточнения и память оформляются инструментами разговора, которые сервер проверяет сразу. Предел исследования (8 кругов) больше не роняет ход. Окно контекста берётся по модели, переполнение сжимает старые результаты и раннюю историю видимо для человека. `AGENTS.md` и `CLAUDE.md` доезжают до Мастера и до исполнителя. Поток ответа пишется в базу не чаще 10 раз в секунду, а SSE просыпается по событию вместо опроса каждые 25 мс. Проверено тестами исходников (`go test ./internal/orchestrator ./internal/app ./internal/storage ./internal/workspace ./internal/httpapi`, `npm --prefix vscode-extension run check` с Node 24, `check-docs`, `check-release-contracts`). Живая приёмка на llmux ещё не выполнялась. Подбор исполнителей по-прежнему стоит между ответом и завершением хода: перенос его в фон затрагивает утверждение наряда и отложен отдельной работой.

Первый живой ход на llmux (Qwen3.8-27B, 25 сентября, «Go-сервис с health-эндпоинтом, PostgreSQL и docker compose») показал три дефекта постановки. Модель взяла `resultKind=code` для записи файлов, и первая попытка задания была отвергнута. Вопросов не было: видимое поведение (ответ при упавшей БД) Мастер записал безопасным дефолтом. Критерии требовали `docker compose up -d --build` и цикл с `curl` — в песочнице без Docker такое не исполняется, и у Point для этих форм нет проверки на хосте. Предыдущий квест с той же задачей остановился на `docker: not found`. Исправлено в схеме `propose_brief`, навыках `master-intake` и `master-criteria` и в ходе: если задание осталось в обсуждении без карточки вопросов, модели даётся ещё один круг. Проверено тестами исходников (`go test ./internal/orchestrator ./internal/domain ./internal/app ./internal/httpapi`, `check-docs`), выложено в `.cache\VSCode-win32-x64` и установленное приложение (SHA-256 ядра совпадает). Повторный живой ход ещё не выполнялся. `make test-go` красный на `go vet` (недостижимый код в `agent_selector_lifecycle_test.go`) и staticcheck (три неиспользуемые функции в `task_intake.go`) независимо от этой правки.

Позднейший прогон этой Go-задачи 25 сентября выявил дефект резервного Flow: при отсутствии `composer.json` подготовка завершалась без действий, а PHP-ориентированный контракт реализации запрещал `go.mod`, `Dockerfile`, `.dockerignore`, Compose и файлы вне `src/config/public`. Реализация дошла до предела 24 шагов, затем её изменения были отвергнуты на `.dockerignore`. По уточнённому решению резервный Flow при ошибке планировщика убран: Point повторяет запрос модели один раз, после второго отказа сообщает ошибку и не запускает исполнителей. Для проектного задания без настроенного планировщика нужен явно выбранный Flow. `go test ./... -count=1`, узкие тесты планировщика и документационный затвор прошли; `go vet` остаётся красным на недостижимом коде в `agent_selector_lifecycle_test.go`, staticcheck — на восьми неиспользуемых функциях вне этой правки. Повторный живой ход и доставка ещё не подтверждены.

Ближайший затвор: повторить от первого сообщения до доставленной ревизии и независимых проверок короткую и среднюю задачу; после этого сверить фактические режимы изоляции, восстановление после перезапуска и причины `blocked` с UI и справочниками. Параллельная оркестрация и самообучение не расширяют обещание продукта, пока этот затвор не пройден.

Открытое решение для целевой модели: текущий evidence gate допускает `completed` с `partial` assurance при ручном критерии или недоступной проверке. Цель в [PRODUCT-VISION.md](PRODUCT-VISION.md) требует отдельной ручной приёмки обязательного ручного критерия. До изменения контракта UI должен явно показывать неполную уверенность, а `completed` нельзя трактовать как полностью проверенный результат.

Исторические результаты описывают состояние на даты записей: [журнал разработки](PROJECT-HISTORY.md).
