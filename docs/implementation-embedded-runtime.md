## Implemented boundaries

- `StageVerifyOutcome.Passed` means machine checks passed. `NeedsReview`, `PendingCriterionIDs` and criterion evidence retain mandatory manual review. Finishing a writer without independent verification produces `implementation_ready`; passing machine checks with pending manual criteria produces `needs_review`. Neither condition claims `acceptancePassed=true`.
- Core diagnostics, the Hub transcript and journal prefer nested evidence when reading contradictory historical completion events. They do not rewrite stored events. The quest card already reads criterion evidence from the final WorkOrder gate.
- The trusted planner supplies `AgentProfile.ManagedVerification` internally. It is excluded from JSON configuration. Managed stages may diagnose problems and keep scope/regression guards, while Point runs the independent acceptance batch. Standalone stages retain their verification obligations.
- Dependency/check events include `phase`, `engine`, `engineVersion` and `securityProfileVersion`. The performance report separates writer preparation, pre-Accept, Accept and shadow Accept. Command/audit times remain nested in tool time. Unmeasured runtime, synchronization, delivery, human-wait and whole-environment costs are explicit.
- Reuse requires approved `deterministic: true` on every nonmanual `verification/run_command` criterion, a matching environment/engine/security identity, dependency fingerprint, tree, image, criteria, commands and policies, and complete audit. Those check commands run with egress denied; dependency preparation keeps separately approved registry access. Legacy approved orders remain ineligible. Stored proof must come from independent `pre_accept`/`accept`, have matching criterion identities and successful checks. Manual criteria remain pending. A newer failure prevents retrieval of an older success, including after shadow disagreement.

## Experimental runtime

`ContainerEngine` replaces the infrastructure command transport while retaining `Backend`, `ProcessExecutor`, Linux volumes, mirror/supervisor audit and `point-sandboxd`. `embedded` supports experimental Moby and Podman transports through a separate Point-owned WSL 2 distribution. Agent commands do not receive engine access. Windows bind execution and live workspace mounting are refused.

`point-runtime.exe` implements install/status/exec/idle. An operator release pack supplies a pinned engine version, rootfs SHA-256, image archive SHA-256 and sandbox image digest. The whole manifest identifies the distribution and control directory. Assets must be regular local files. A mismatched ownership record cannot adopt an existing distribution. Interrupted import/image preparation can be retried with the same pack after reboot.

Provisioning preserves other distributions, Windows Docker contexts and global WSL settings. Runtime commands and active workspaces hold process-owned leases under an interprocess control lock. Idle termination affects only the owned distribution after ten minutes without activity or live leases, retaining its disk. Crash releases OS leases. Unknown command outcomes remain subject to the existing sandbox journal/audit recovery; commands are not replayed.

The readiness probe verifies engine/image versions, disabled Windows automount and interop, nonroot UID, dropped capabilities, no-new-privileges, read-only root, network-none and cgroup CPU/memory/PID limits. Missing or failing proof leaves embedded capabilities unavailable and execution blocked. This probe is an initial gate; it does not replace the complete network/files/process/recovery integration suite.

Build and provision from a reviewed release pack:

```powershell
node scripts/build-core.mjs
powershell -NoProfile -File scripts/build-point-runtime-pack.ps1 -Engine moby -BaseImage <debian-or-ubuntu-repo@sha256:digest> -PackageVersion <exact-apt-version> -SandboxImage <local-sandbox-image> -OutputDirectory <new-pack-directory>
powershell -NoProfile -File scripts/setup-point-runtime.ps1 -ManifestPath <pack-directory>/runtime.json
```

The PowerShell pack builder uses a Docker-compatible release build environment. Alternatively, `scripts/build-point-runtime-wsl-pack.py` prepares an owned WSL guest from a checksum-verified rootfs and installs an exact engine package version from signed apt repositories. It disables Windows automount/interop before first boot and refuses an existing distribution. This path was used on the current PC without Docker Desktop. `scripts/build-point-runtime-matrix-image.py` verifies both base OCI archives share their configuration/layers, adds pinned PHP/Composer to the existing Node/Go image and emits new immutable packs. Docker manifest digests and Podman configuration IDs differ even for identical OCI content; execution IDs and the common content digest are recorded separately.

Base image/rootfs, package versions and asset hashes are mandatory inputs; no unverified download URL or implicit latest engine is installed. Pack supply-chain review, license notices, source obligations for Linux dependencies, signing/update/rollback and an installer UI are outstanding release work. `packages.txt` and the rootfs package copyright files provide inventory inputs, not completed release approval.

Opt in before starting Point: `POINT_SANDBOX_BACKEND=embedded`, `POINT_SANDBOX_WORKSPACE=volume`, `POINT_EMBEDDED_RUNTIME=<absolute-pack-manifest>`. Reuse additionally requires `POINT_VERIFY_SERVICE=on` and eligible approved criteria. Existing executions must resume under their original pinned engine. No host fallback is provided.

Moby ships with Point. `scripts/bundle-point-moby.ps1 -PointRoot <Point root> -PackPath <pack directory>` verifies the pack against its manifest and places it in the extension's `bin/moby` beside `point-runtime.exe`; on the same volume the files are hard links, otherwise copies. The pack is excluded from the VSIX (`.vscodeignore`), so `ship-hub-extension.ps1` keeps it, while a full `distribution/build-code-oss.ps1` rebuild recreates the extension directory and must be followed by the bundle step. The extension resolves `bin/moby/runtime.json` itself: without an explicit `localAgent.sandboxBackend` such a Point runs on `embedded`, an explicit choice (`filtered-copy`, `docker`) still wins, and an installation without the pack keeps the old `filtered-copy` default. `localAgent.embeddedRuntimeManifest` is an optional override for a separately verified pack; if its file is missing, the shipped pack is used instead of leaving execution unavailable. Changing any engine setting offers a core restart. The selected pack must be Moby. Recommended `sandboxCPUs=2`, `sandboxMemoryGiB=2` match the measured configuration; `verificationReuse` defaults to `on` for every backend since 2026-10-03. Embedded launch enforces volume storage, warm containers, verified download caches, 256 PIDs, nonroot execution and no live Windows mounts. Project settings cannot replace the engine, manifest or quotas. Changes take effect for new core launches; an already attached core and its quests retain their original environment. Runtime ownership, leases and the guest disk live in `%LOCALAPPDATA%\Point\runtime\<manifest digest>`. A process from an MSIX-packaged tool (for example an agent app) sees a virtualized `%LOCALAPPDATA%`; a runtime provisioned from it is invisible to Point and must be provisioned or moved from an ordinary process.

The bridge must be adjacent to the installed core. Developer test binaries may explicitly supply an absolute trusted `POINT_RUNTIME_BRIDGE` path to the built `point-runtime.exe`. No bridge is resolved relative to a project or current working directory.

## Measurements and remaining gates

The live dependency quest benchmark now defaults to `quest_e94cc95ffab7869553c15323`, alternates three bind/shadow and three volume/shadow trials, then runs volume/on. It copies the database read-only and sources into separate test directories, freezes declared Jest suites, pins Qwen3.8-27B without model fallback, preserves manual review and records delivery/reuse provenance. It fails environment preflight before model calls. Approval-to-receipt wall time is recorded; whole-environment resources and human wait remain unmeasured in this harness.

`node scripts/compare-point-runtimes.mjs <raw-samples.json>` evaluates complete raw samples. It requires all three projects (`node-typescript`, `go`, `php`), cold and warm regimes, at least three repetitions, fixed source/criteria/commands/dependency/image/environment/policy/resource inputs, full-quest evidence and verified delivery. It reports medians/ranges and uses equal project weights with geometric relative warm time. Qualification requires at least 30% warm acceleration, at most 10% memory/CPU growth and at most 10% individual cold/warm regression. Within 5% of the fastest qualifying time, lower peak memory wins, then CPU time. Missing resources, audit, behavior, receipt or manual-review proof blocks qualification.

Raw sample schema: `schema:1`, `baseline:<configuration-id>`, `samples:[...]`. Each sample includes `id`, `configuration`, `project`, `regime`, `kind:"full_quest"`, `resourceCoverage:"whole_environment"`, engine/version/runtime digest, storage/verify modes, model/route/fallback, `approvedAt`, `deliveredAt`, separate `humanWaitMs` and `installationMs`, receipt ID and local evidence path. Resource metrics are CPU-time ms, peak/idle memory bytes, disk read/write bytes, storage bytes and network bytes. `pins` includes the ten input digests/profile names used by the comparator. `quality` includes runtime security parity, mandatory tests, independent behavior, scope, complete audit, correct verdicts, verified delivery and preserved manual criteria. The smoke fixtures are synthetic and are never performance evidence.

The fixed Node/TypeScript, Go and PHP fixtures and coordinator are implemented in `internal/acceptance/runtime_matrix_*_test.go` and `scripts/run-point-runtime-matrix.py`. They use new directories/databases, original immutable tests/locks, a pending manual criterion, a pinned model/route and a clean independent behavior probe. Failed trials remain in the raw ledger. Operation replay uses fixed source bytes/commands without a model and cannot qualify a full-task speedup. `--max-tasks` and fewer than three trials are diagnostic pilots only.

`scripts/point_runtime_metrics.py` assigns the gated test child to a Windows job, including CPU/IO from exited children, and samples protected WSL/infrastructure processes through CIM. Guest block/NIC counters and the model's encrypted TCP byte counter are saved alongside raw frames. Other running WSL distributions make attribution fail; only recorded, owned, inactive Point guests may be stopped. CPU from job members is not counted again as infrastructure. Memory is a sum of sampled working sets at 750 ms, not an instantaneous hardware high-water mark. Host logical IO includes pipes; guest physical block IO is retained separately in raw evidence. Their aggregate is an IO-volume indicator, not exclusively physical disk traffic. Storage includes the owned VHD, pack assets and trial artifacts, deduplicating hard links. The initial idle frame is measured before approval. Already-provisioned trials record zero installation time; pack preparation/installation is separate and cannot be inferred from task timing.

Cold trials use fresh project/database/dependencies and a provisioned engine ready before approval; owned embedded guests also restart before preparation, which is recorded separately. Warm trials immediately follow cold on the same guest, still with a fresh project/database and per-quest verified caches. Host page caches are not flushed because that affects unrelated applications. Replay/cache keys include the absolute trial identity, avoiding collisions with earlier pilots. Optimization ablations explicitly pin `POINT_SANDBOX_WARM_CONTAINER=off` or `POINT_SANDBOX_DOWNLOAD_CACHE=off`; the latter disables all manager-owned dependency/build cache mounts. Installed Go modules then live in that workspace's excluded `.point/gomod` directory, so subsequent offline commands can use installed dependencies while independent portable clones still install afresh. Default values remain on. A changed optimization mode changes runtime verification identity and cannot silently reuse an old workspace/proof.
