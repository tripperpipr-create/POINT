# Интеграция GitLab через MCP

Статус на 25 сентября 2026 года: этап 1 собран в исходниках — ядро MCP,
плагин GitLab, вкладка «Интеграции», окно GitLab и карточка MR. Проверен
тестами на фикстурах и смоуками вебвью. Живой приёмки на GitLab владельца
(19.3.2, внутренняя сеть) ещё не было: порядок — в разделе «Живая приёмка».

## Как устроено

Point не ходит в REST API GitLab сам. Он запускает MCP-сервер GitLab как
долгоживущий процесс stdio и вызывает его инструменты из ядра. Модель в этом не
участвует:

- окно «GitLab» (списки MR и пайплайнов) и карточка MR получают данные
  детерминированными вызовами инструментов;
- кнопки «Комментировать», «Одобрить», «Merge», «Перезапустить» — действие
  владельца: оно выполняется сразу и пишется в журнал интеграций;
- агентам и Мастеру инструменты GitLab на этапе 1 не выдаются.

## Сервер и рецепт запуска

Закреплён `@zereight/mcp-gitlab@2.1.66` (MIT). Целостность пакета из реестра npm:
`sha512-KiWiaRzQQw8i+CFwY4zQgsVrLAbj81Dok3ZUqdUIYOhQIs5DOskxoZtqNp1qjdBRYKD03HPmV+4Wv1OinyDfXw==`.

```text
npx -y @zereight/mcp-gitlab@2.1.66
GITLAB_API_URL=https://<ваш GitLab>/api/v4
GITLAB_PERSONAL_ACCESS_TOKEN=<секрет, из SecretStorage>
GITLAB_TOOLSETS=merge_requests
GITLAB_TOOLS=<21 инструмент из таблицы ниже>
GITLAB_PERMISSION_MODE=modify
GITLAB_DENIED_TOOLS_REGEX=^discover_tools$
```

Замеры спайка (`tools/list`, сервер запущен с поддельным адресом — список
инструментов к GitLab не обращается):

| Настройка | Инструментов | Схемы в JSON |
| --- | --- | --- |
| по умолчанию | 118 | 174 КБ |
| рецепт выше | 46 | 77 КБ |
| только нужные Point | 21 | 39 КБ |

Сократить список до 21 средствами самого сервера нельзя. `GITLAB_TOOLS`
добавляет инструменты к наборам, а не сужает их, а `GITLAB_DENIED_TOOLS_REGEX`
ограничен 200 символами. Поэтому главная граница — у Point:
- адаптер вызывает только инструменты из таблицы;
- инструменты сервера по умолчанию выключены для агентов;
- `GITLAB_PERMISSION_MODE=modify` на стороне сервера убирает удаление и
  разрушительные инструменты;
- `discover_tools` запрещён: он добавляет инструменты во время работы.

Для внутреннего сертификата GitLab сервер читает `GITLAB_CA_CERT_PATH`, Node —
`NODE_EXTRA_CA_CERTS`.

## Права токена

Для просмотра достаточно `read_api`. Комментарии, одобрение, merge и перезапуск
джоба требуют `api`. С токеном только на чтение GitLab отказывает в действии, и
окно показывает причину `auth` с подсказкой про права токена.

## Экран → инструмент

Ответы сервера — JSON объектов REST API GitLab в `content[0].text` (без
`structuredContent`). Исключение — лог джоба: он приходит простым текстом.

| Экран | Инструмент | Аргументы Point |
| --- | --- | --- |
| Кто я (для «На моём ревью») | `whoami` | — |
| Проект по git remote | `get_project` | `project_id` = путь `group/name` |
| MR: мои / на ревью / все открытые | `list_merge_requests` | `project_id`, `state=opened`, `author_username` / `reviewer_username` / без фильтра |
| Карточка MR | `get_merge_request` | `project_id`, `merge_request_iid` |
| Одобрения | `get_merge_request_approval_state` | `project_id`, `merge_request_iid` |
| Обсуждение | `mr_discussions` | `project_id`, `merge_request_iid`, `page`, `per_page`; ответ `{items, pagination}` |
| Список изменённых файлов | `list_merge_request_changed_files` | `project_id`, `merge_request_iid` |
| Diff файла | `get_merge_request_file_diff` (запасной — `get_merge_request_diffs`) | `project_id`, `merge_request_iid`, `file_paths` |
| Содержимое файла для diff IDE | `get_file_contents` | `project_id`, `file_path`, `ref` = `diff_refs.base_sha` / `head_sha` |
| Комментарий | `create_merge_request_note` | `project_id`, `merge_request_iid`, `body` |
| Ответ в нить | `create_merge_request_discussion_note` | + `discussion_id` |
| Одобрить / снять | `approve_merge_request` / `unapprove_merge_request` | + `sha` для одобрения |
| Merge | `merge_merge_request` | + `sha` (ожидаемая голова), `should_remove_source_branch` |
| Пайплайны ветки | `list_pipelines` | `project_id`, `ref` |
| Пайплайны MR | `list_merge_request_pipelines` | `project_id`, `merge_request_iid` |
| Пайплайн и джобы | `get_pipeline`, `list_pipeline_jobs` | `project_id`, `pipeline_id` |
| Лог джоба | `get_pipeline_job_output` | `project_id`, `job_id`, `limit`, `offset` |
| Перезапуск джоба | `retry_pipeline_job` | `project_id`, `job_id` |

Если у подключённого сервера инструмента нет, экран сообщает «сервер этого не
умеет» и называет инструмент. Остальные экраны работают.

## Ядро

- `internal/integrations/gitlab` — рецепт запуска, сверка возможностей с
  инструментами сервера (`Capabilities`), разбор `git remote` и адаптер экранов.
  Адаптер знает только инструменты из таблицы и режет недоверенный текст:
  - описание MR — до 64 КБ;
  - заметка — до 16 КБ;
  - diff — до 512 КБ;
  - файл — до 1 МБ;
  - хвост лога — до 256 КБ, без управляющих кодов и через `security.Redact`.

  Ссылка `web_url` чужого источника отбрасывается.
- `internal/app/gitlab.go` — плагин. У него один MCP-сервер с постоянным id
  `mcp-gitlab`, и токен лежит по ссылке
  `point.mcp.mcp-gitlab.env.GITLAB_PERSONAL_ACCESS_TOKEN`. Смена адреса или
  сертификата меняет команду запуска и требует нового доверия. Смена токена
  доверия не сбрасывает. Форма «любого MCP» сервер плагина не правит.
- Привязка папки хранится в `gitlab_bindings`:
  - `auto` — проект по `git remote get-url origin`: scp-вид, `ssh://`,
    `https`; учётные данные из адреса выбрасываются, префикс пути GitLab
    снимается;
  - `manual` — путь, названный владельцем;
  - `all` — MR владельца по всем проектам.

  Ветка для пайплайнов — текущая ветка папки. Если узел SSH отличается от узла
  GitLab (`ssh.gitlab…`), проект выбирается вручную.
- `internal/app/gitlab_screens.go` — экраны и действия. Ответ всегда
  `{state, reason, problem, fix, data}`; маршруты описаны в [api.md](api.md).
- Действие владельца выполняется сразу и пишется в `integration_actions`:
  инструмент, цель (`группа/проект!iid`), итог и ошибка. Текст комментария не
  хранится — только sha256 и длина.
- Merge требует `confirmed:true` и `expectedSha`: GitLab откажет, если голова
  MR ушла вперёд после того, как владелец её увидел.
- Риски инструментов для будущих агентов заданы плагином, а не подсказками
  сервера:
  - `merge_merge_request` — CRITICAL;
  - запись (комментарии, одобрение, перезапуск) — HIGH;
  - чтение — LOW.

  Все инструменты для агентов выключены.

## В IDE

- **Гильдия → «Интеграции».** Карточка плагина: адрес GitLab, личный токен и
  путь к сертификату CA. Токен уходит в SecretStorage IDE и в память ядра.
  После сохранения сервер ждёт «Доверяю…»: окно доверия показывает точную
  команду `npx`, аргументы и переменные. Ниже — свои MCP-серверы (форма или
  импорт `mcp.json`), таблица инструментов с риском и журнал действий.
- **Окно GitLab** — значок `git-merge` на рейке и строка «GitLab» в «Окнах
  инструментов». Под шапкой — проект окна: по git remote, выбранный вручную
  или «все мои проекты». Разделы:
  - MR «Мои / На ревью / Все открытые»;
  - пайплайны текущей ветки с джобами: лог джоба открывается документом
    редактора, джоб можно перезапустить.
- **Карточка MR** — вкладка редактора:
  - шапка: ветки, состояние, одобрения, пайплайн;
  - вкладки «Обзор», «Обсуждение» (ответ в нить и новый комментарий),
    «Изменения» (файл открывается сравнением IDE: база MR слева, голова справа)
    и «Пайплайн».

  «Одобрить» передаёт увиденную голову. «Merge» спрашивает подтверждение в
  модальном окне IDE и передаёт ту же голову; флажок «удалить ветку» — там же.
- **«Открыть в GitLab»** открывает только ссылки на подключённый сервер.

## Живая приёмка

1. Подключить плагин с адресом и токеном, доверить запуск, нажать «Проверить»:
   сервер `2.1.66`, 46 инструментов, из них 21 известен Point.
2. Открыть окно GitLab в папке с `origin` на этот GitLab. Проверить три списка
   MR и пайплайны ветки; в «Все мои проекты» — MR по всем проектам.
3. В тестовом MR:
   - комментарий и ответ в нить;
   - одобрить и снять одобрение;
   - открыть diff файла и лог упавшего джоба;
   - перезапустить джоб;
   - merge с удалением ветки;
   - проверить журнал действий.
4. Перезапустить ядро (закрыть и открыть окно): список MR снова открывается без
   повторного ввода токена.
5. Снять настоящие ответы инструментов в `testdata/zereight-2.1.66/responses/`
   вместо синтетических, вычистив узел, имена и токены.
6. На Windows проверить `npx.cmd`, сертификат внутреннего CA и задержки VPN.

## Фикстуры

`internal/integrations/gitlab/testdata/zereight-2.1.66/`:
- `manifest.json` — версия, целостность, протокол, рецепт, дата;
- `tools-list.json` — определения 21 инструмента, снятые со сборки 2.1.66;
- `responses/` — по файлу на инструмент: адаптер (`client_test.go`) и поддельный
  сервер в тестах ядра (`internal/app/gitlab_test.go`) проигрывают их.

Образцы ответов инструментов пока синтетические. Они собраны по схемам ответов
сервера (`schemas.js` 2.1.66) и REST API GitLab и помечены в `manifest.json`.
Заменить их снятием с GitLab владельца — часть живой приёмки.
