# Окно поиска Point

Техническое задание на своё окно поиска — то, что открывается двойным Shift.
Актуально для Point `1.2.2` на 2 сентября 2026 года. Реализация:
[`distribution/resources/point-search-window.ts.txt`](../distribution/resources/point-search-window.ts.txt)
(слой оболочки) и раздел «Своё окно поиска» в
[`distribution/resources/point-workbench.css`](../distribution/resources/point-workbench.css).

## Зачем оно есть

У JetBrains поиск один на вид и несколько по существу: «Найти всё» ищет файл по
имени и символ по имени, «Найти в файлах» — строку в содержимом. Палитра
Code-OSS даёт первое и не даёт второго: `workbench.action.findInFiles` открывает
панель поиска сбоку, то есть уводит из окна вместо того, чтобы ответить в нём.
Плюс сама палитра выглядит формой: поле в рамке с кольцом фокуса внутри
всплывающего окна.

Поэтому у Point своё окно: три вкладки, одна строка ввода, один список, ответ
внутри окна.

## Границы

**В задаче.** Поиск файла по имени, символа по имени, строки в содержимом;
недавние файлы на пустом запросе; открытие найденного в текущей или соседней
колонке.

**Не в задаче.** Замена текста, регулярные выражения, фильтры по маске,
поиск вне проекта, вкладка «Действия» (реестр команд), группировка совпадений по
файлам. Каждое из этого — отдельное решение: замена и регулярки требуют своей
формы и своего подтверждения, «Действия» — своего источника, а группировка
меняет модель списка со строк на дерево.

**Чего окно не делает никогда.** Не заводит собственный индекс, не ходит в ядро
Point и не хранит свою копию истории. Поиск обязан работать, когда ядро не
поднято, и обязан отвечать то же, что встроенная панель поиска: две правды о
содержимом проекта в одном продукте — дефект, а не удобство.

## Источники данных

| Что | Источник | Почему именно он |
| --- | --- | --- |
| Файлы по имени | `ISearchService.fileSearch` | Тот же поставщик, что у встроенного быстрого перехода: уважает `files.exclude`, `.gitignore` и лимиты |
| Строка в содержимом | `ISearchService.textSearch` | Тот же, что у панели поиска; даёт позиции совпадений и превью строки |
| Символы | `getWorkspaceSymbols` | Тот же, что у штатного перехода к символу; работает через языковые службы |
| Недавние | `IEditorService.getEditors(MOST_RECENTLY_ACTIVE)`, затем `IHistoryService.getHistory()` | Вкладки знают текущее, история помнит закрытое; одной истории мало — в свежем окне она пуста |
| Значок строки | `getIconClasses` | Та же тема значков, что рисует Инвентарь |
| Путь к файлу | `ILabelService.getUriLabel({ relative: true })` | Один способ показывать путь на весь продукт |

## Вкладки

Порядок в полосе и в обходе клавишей Tab: **Файлы → Символы → Текст**.

| Вкладка | Запрос | Пауза | Потолок | Порог |
| --- | --- | ---: | ---: | ---: |
| Файлы | имя файла, нечёткое совпадение | 80 мс | 50 строк | 1 знак |
| Символы | имя символа | 150 мс | 50 строк | 1 знак |
| Текст | подстрока, без регистра и регулярок | 220 мс | 50 строк, не больше 4 на файл | 2 знака |

Паузы разные не для красоты: поиск по именам идёт по прогретому списку и
отвечает мгновенно, поиск по содержимому — работа по диску. Порог в два знака у
текста — защита от обхода всего проекта ради буквы, которая есть в каждом втором
файле.

Потолок в 50 строк снимает вопрос о виртуализации списка: до пятидесятой строки
не доходят ни стрелками, ни глазами — уточняют запрос.

## Клавиатура и мышь

| Действие | Как |
| --- | --- |
| Открыть поиск по файлам | двойной Shift, `Ctrl+N` |
| Открыть поиск по тексту | `Ctrl+Shift+F` |
| Открыть поиск по символам | `Ctrl+Alt+Shift+N` |
| Другая вкладка | `Tab` вперёд, `Shift+Tab` назад, щелчок по вкладке |
| Ходить по строкам | `↑` `↓`, `PageUp` `PageDown` (шаг 10) |
| Открыть | `Enter`, щелчок по строке |
| Открыть в соседней колонке | `Shift+Enter`, `Shift`+щелчок |
| Закрыть | `Esc`, щелчок мимо окна |

**Три сочетания принадлежат слою оболочки, а не расширению.** Раскладка
расширения весит `BuiltinExtension` (300) во встроенной поставке и
`ExternalExtension` (400) в установленной, поэтому перевес слоя считается от
верхней ступени: `KeybindingWeight.ExternalExtension + 50`. Прежние
`WorkbenchContrib + 50` (250) проигрывали обоим, и замер живого окна это
показал: `Ctrl+N` открывал квик-пик «Поиск везде», `Ctrl+Shift+F` — Quick
Search, `Ctrl+Alt+Shift+N` — «Перейти к классу»; окно не открывалось ни на одном
из трёх. Второе объявление тех же сочетаний убрано из манифеста расширения —
одно сочетание, одно объявление. Обе стороны сторожит
[`scripts/check-point-navigation.mjs`](../scripts/check-point-navigation.mjs).
Пользовательскую раскладку перевес не трогает: `keybindings.json` разбирается
отдельной ступенью и выигрывает у любого веса по умолчанию.

**Двойной Shift выражается только счётом нажатий.** Раскладка Code-OSS знает
лишь «модификаторы плюс клавиша», а здесь клавиша и есть модификатор. Правило:
считается нажатие, при котором Shift нажали и отпустили, ничего между ними не
нажимая и не удерживая других модификаторов; окно между двумя такими нажатиями —
350 мс. Прописная буква в счёт не идёт: между нажатием и отпусканием там есть
чужая клавиша. Автоповтор при удержании сбрасывает счёт.

Повторный вызов при открытом окне не открывает второе: переводит открытое на
нужную вкладку и возвращает фокус в строку ввода.

Выделение в редакторе подставляется в запрос при открытии — кроме
многострочного: им открывают окно, а не ищут.

## Состояния

Каждое состояние обязано отличаться от соседнего словами, а не пустотой.

| Когда | Что показывает |
| --- | --- |
| Пустой запрос, вкладка «Файлы» | Недавние файлы, счётчик «недавние: N» |
| Пустой запрос, «Символы» и «Текст» | «Введите запрос» |
| Пустой запрос, истории нет | «История пуста» |
| Запрос короче двух знаков на «Тексте» | «Нужно хотя бы два знака» |
| Проект не открыт | «Проект не открыт» |
| Нет ни одной языковой службы | «Языковая служба не подключена — символы искать нечем» |
| Поиск отработал, совпадений нет | «Ничего не найдено» |
| Поиск отказал | «Поиск не удался: <причина>» |
| Идёт запрос | Черта под строкой ввода берёт акцентный тон |

Отдельно: отсутствие поставщика символов **не** равно пустой выдаче. Пустая
выдача утверждает «в проекте нет ничего похожего», а считать символы в этот
момент попросту некому.

## Вид

Геометрия повторяет палитру: два окна поиска в одном продукте не должны выглядеть
как два разных продукта.

| Величина | Значение |
| --- | --- |
| Ширина окна | `min(760px, 100vw − 48px)` |
| Отступ сверху | `14vh` |
| Высота полосы вкладок | 36 px |
| Высота строки ввода | 38 px, кегль 14 |
| Высота строки результата | 28 px |
| Высота подвала | 26 px |
| Боковое поле | 12 px |
| Скругление | `--point-r-lg` (8 px) |
| Тень | два слоя: `0 24px 64px rgba(0,0,0,.6)` и `0 2px 10px rgba(0,0,0,.45)` |

Величины из таблицы — внешние: рамка считается внутрь (`box-sizing: border-box`
у окна, полосы вкладок, строки ввода и подвала). Без этого замер живого окна
давал 762 вместо 760 и 39 вместо 38 — ровно на толщину собственных границ.

Кегль строки ввода задан отдельным правилом с длинным селектором: у Code-OSS
есть `.monaco-workbench input { font-size: 100% }` — класс плюс тип, вес выше
одиночного класса, и он возвращал строку к 13px, унаследованным от оболочки.

Полоса вкладок, строка ввода и подвал не усаживаются (`flex: 0 0 auto`),
усаживается только список. Окно — колонка с потолком `62vh`, и на полной выдаче
общее правило усадки дожимало соседей: замер на пятидесяти строках показал
полосу вкладок 29 вместо 36 и подвал 12 вместо 26, то есть путь выбранной строки
складывался вдвое ровно тогда, когда он нужнее всего.

**Строка результата.** Слева значок файла, дальше имя, сразу за именем —
приглушённый путь, обрезанный **с начала** (`direction: rtl` плюс
`unicode-bidi: plaintext`). Хвост пути отвечает на вопрос «который из
одноимённых», начало у всех совпадает. У текстовой вкладки слева стоит сама
строка кода моноширинным набором, а `файл:строка` уходит вправо: путь после
длинной строки кода оказался бы за краем окна.

**Подсветка совпадения** — подложка `color-mix(--point-ember 26%)`, а не один
цвет: акцентная буква посреди моноширинной строки теряется. У выбранной строки
подложка на ступень плотнее, иначе на её собственной заливке подсветка пропадает.
Куски для подсветки берутся у `scoreFuzzy2` — тем же способом, что подсвечивает
палитра.

**Выбранная строка** помечена подложкой `--point-tint-selected` и полосой
`inset 2px 0 0 --point-ember` — это общая договорённость списков оболочки, и
окно поиска её не нарушает.

**Подвал.** Слева полный путь выбранной строки моноширинным набором, справа
счётчик: «файлов: N», «символов: N», «совпадений: N», «недавние: N». Подсказок
клавиш в подвале нет — место отдано пути.

**Вкладка** несёт своё сочетание рядом с названием (`Shift Shift`,
`Ctrl+Alt+Shift+N`, `Ctrl+Shift+F`): три привычки ведут в разные вкладки, и знать
о них нужно там, где выбирают. Активная помечена полосой по нижней кромке ряда —
не тенью внутрь таблетки: тень повторяет скругление и загибается на концах.

## Доступность

- Окно — `role="dialog"` с именем, список — `role="listbox"`, строка —
  `role="option"` с `aria-selected`; вкладки — `role="tab"` с `aria-selected`.
- Фокус при открытии — в строке ввода; кольцо фокуса у неё снято намеренно:
  окно открывается уже с курсором внутри, и кольцо возвращает ту самую коробку,
  ради снятия которой окно и заводилось.
- Любая надпись мельче 18.66 px обязана давать контраст не ниже 4.5 против
  фактического фона. Отсюда `--point-muted` у пути, счётчика и сочетаний вкладок:
  `--point-faint` на подложке окна даёт 3.8.
- Высота строки 28 px и высота вкладки 28 px — цель указателя не меньше 24 px.

## Отклик

Требование: на проекте средних размеров ответ вкладки «Файлы» не дольше 250 мс,
вкладки «Текст» — не дольше 450 мс, считая паузу перед запросом.

Механика, которая это обеспечивает:

1. **Кэш списка файлов.** При открытии окна фоном идёт один обход проекта под
   собственным ключом (`cacheKey`), дальше запросы отбираются из готового
   списка. Без ключа каждое нажатие клавиши обходило проект заново — на большом
   репозитории это секунды на букву.
2. **Кэш снимается при закрытии окна** (`clearCache`): он живёт ровно столько,
   сколько открыт поиск.
3. **Отмена предыдущего запроса** токеном при каждом новом вводе.
4. **Порядковый номер запроса**: ответ, пришедший после следующего ввода,
   отбрасывается — иначе медленный старый ответ затирал бы свежий.

Замер 2 сентября 2026 года на этом репозитории, от ввода до появления строк:

| Вкладка | Запрос | Отклик |
| --- | --- | ---: |
| Файлы | companion | 166 мс |
| Файлы | workbench | 150 мс |
| Файлы | point-search | 149 мс |
| Текст | workspaceId | 324 мс |
| Текст | companionIdeContext | 316 мс |

Из них 80 и 220 мс — собственная пауза: служба отвечает за 70–100 мс.

## Где живёт и как собирается

Окно — слой оболочки, а не расширение и не вебвью: всплывающее окно поверх
редактора в модели расширений VS Code не выражается (панель уходит во вкладку
редактора или в боковую панель), а данные ему нужны от служб самой оболочки.

- Исходник слоя: `distribution/resources/point-search-window.ts.txt`.
- Накладывает [`distribution/apply-overlay.mjs`](../distribution/apply-overlay.mjs):
  копирует файл в `src/vs/workbench/contrib/search/browser/pointSearchWindow.contribution.ts`
  и добавляет одну строку импорта во вклад поиска. Команды, сочетания и вклад
  двойного Shift регистрирует сам слой — апстрим правится одной строкой.
- Поле поиска в верхней полосе вызывает `point.searchWindow` (заплата
  командного центра в том же `apply-overlay.mjs`).
- Правка слоя требует полной пересборки Code-OSS. Правка только стилей —
  нет: блок стилей дописывается в собранный `workbench.desktop.main.css`, после
  чего обязателен `node distribution/refresh-product-checksums.mjs`, иначе окно
  встретит «установка повреждена».

## Как проверять

```powershell
# типы всего дерева со слоем — без часовой сборки
cd .cache\code-oss; node_modules\.bin\tsc --noEmit -p src\tsconfig.json

# полная сборка
powershell -File distribution\build-code-oss.ps1 -SkipInstall -SkipInstaller -PythonPath <путь к python.exe>

# оформление живого окна: контраст, цели, фокус, наведение, перекрытие, обрезка
powershell -File scripts\test-point-workbench-design.ps1 -Scenario file

# само окно поиска: сочетания, вкладки, состояния, геометрия, роли, отклик
# и сквозная цепочка. Папка проекта нужна своя: замеры отклика сняты на нём.
powershell -File scripts\test-point-workbench-design.ps1 -Scenario file `
  -Probe scripts\probe-point-search-window.mjs -Workspace .

# окно ещё живо после правок
powershell -File scripts\smoke-code-oss-renderer.ps1
```

Аудит оболочки окно поиска не видит: до него нужно дойти двойным Shift, а этого
не делает ни один сценарий стенда. Поэтому требования ТЗ проверяет свой зонд —
[`scripts/probe-point-search-window.mjs`](../scripts/probe-point-search-window.mjs).
Он открывает окно вводом, а не вызовом команды: подмену сочетания чужой командой
видно только так. Ненулевой код возврата и список `провалы` в отчёте — это
нарушенные пункты ТЗ, по одному на строку.

Сценарии стенда и правила замера описаны в [VISUAL-LOOP.md](VISUAL-LOOP.md).

Обязательная сквозная проверка при изменении поиска — не «окно открылось», а
цепочка: открыть окно двойным Shift → найти файл → `Enter` → убедиться, что
открылась вкладка редактора с этим файлом → снова открыть окно → на пустом
запросе увидеть этот файл в недавних. У стенда профиль чистый, и «недавние»
доказываются только так. Эту цепочку зонд проходит сам — руками её больше не
повторяют.

Перед сборкой убедиться, что `.cache\VSCode-win32-x64` никто не держит:
`gulp` начинает со сноса этой папки, а осиротевшие `Point.exe` и `point-core.exe`
от прошлых прогонов роняют сборку на `EBUSY: rmdir`.

## Открытые вопросы

- **Вкладка «Действия».** Источник — реестр команд плюс их сочетания; ложится
  тем же слоем. Вопрос не в коде, а в том, чем она отличается от палитры Code-OSS,
  которая уже умеет действия.
- **Поиск вне проекта** (флажок «Include non-project items» у JetBrains) — это
  другой запрос к `ISearchService`, не другое окно.
- **Группировка совпадений по файлам** на вкладке «Текст» превратит список в
  дерево; сейчас модель — плоский список строк, и все клавиши описаны для него.
- **Вспомогательные окна.** Двойной Shift слушает только главное окно: в окнах
  Хаба и статистики поиска проекта нет. Если он там понадобится, слушателя нужно
  заводить на каждое окно, а не на `mainWindow`.
