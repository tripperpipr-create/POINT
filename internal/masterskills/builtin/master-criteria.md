Критерии должны доказывать запрошенный результат, а не просто завершение исполнителя. «Найди баги» — диагностика, не исправление. Для диагностики reproduction может ожидать ненулевой код выхода; verification требует успешной проверки; manual — содержательная проверка человеком.
У manual только id, text, kind: без tool, arguments, expectedExitCode. Для verification/reproduction нужны существующие tool и arguments; команда оболочки — run_command с {"command":"..."}, не shell, bash, terminal, pytest или npm. Не выдумывай команды тестирования: сначала прочитай манифест. Команды verification и reproduction исполняются в песочнице исполнителя: Docker там нет, сервисы на localhost хоста не видны. Docker Compose Point проверяет сам на хосте после доставки, и только такими arguments для run_command: `docker compose build`; `docker compose up -d`; ответ сервиса `{"command":"curl -sf http://localhost:ПОРТ/health","expectJson":{"status":"ok","db":"up"}}` — ждёт 200 и перечисленные поля (без expectJson у /health — только status=ok), поэтому поле, которое доказывает результат, называй явно; сбой зависимости `{"command":"docker compose stop СЕРВИС","url":"http://localhost:ПОРТ/health","expectStatus":200,"expectJson":{"db":"down"},"recoverJson":{"db":"up"}}` — Point остановит сервис, дождётся ответа с этим кодом и полями, поднимет сервис и проверит восстановление. Код и поля бери из согласованного поведения. Такой сбой — verification, не manual. Прочие проверки через Docker или поднятый сервис не исполнятся — оформляй их manual. Если результат иначе не проверить, способ проверки — существенное уточнение к человеку. Если команды запрещены, результат — только код в ответе или проверка ещё не установлена, используй конкретный manual либо существенное уточнение. Не обещай найти абсолютно все ошибки.
