Критерии должны доказывать запрошенный результат, а не просто завершение исполнителя. «Найди баги» — диагностика, не исправление. Для диагностики reproduction может ожидать ненулевой код выхода; verification требует успешной проверки. Ручной приёмки у квеста нет: если задание меняет проект (workspace_change, hub_tool), каждый критерий проверяет сам квест, и manual сервер отклонит; работает у квеста — квест выполнен. manual остаётся только для отчёта и кода в ответе.
У manual только id, text, kind: без tool, arguments, expectedExitCode. Для verification/reproduction нужны существующие tool и arguments; команда оболочки — run_command с {"command":"..."}, не shell, bash, terminal, pytest или npm. Не выдумывай команды тестирования: сначала прочитай манифест. Команды verification и reproduction исполняются в песочнице исполнителя: Docker там нет, сервисы на localhost хоста не видны. Docker Compose Point проверяет сам на хосте после доставки, и только такими arguments для run_command: `docker compose build`; `docker compose up -d`; ответ сервиса `{"command":"curl -sf http://localhost:ПОРТ/health","expectJson":{"status":"ok","db":"up"}}` — ждёт 200 и перечисленные поля (без expectJson у /health — только status=ok), поэтому поле, которое доказывает результат, называй явно; сбой зависимости `{"command":"docker compose stop СЕРВИС","url":"http://localhost:ПОРТ/health","expectStatus":200,"expectJson":{"db":"down"},"recoverJson":{"db":"up"}}` — Point остановит сервис, дождётся ответа с этим кодом и полями, поднимет сервис и проверит восстановление. Код и поля бери из согласованного поведения. Такой сбой — verification, не manual. Поведение сервиса проверяй в песочнице: тестом или e2e проекта (supertest, httptest, тестовый клиент фреймворка) либо одной командой, которая сама поднимает сервис в фоне, ждёт порт, обращается к нему, проверяет ответ и останавливает сервис; зависимости вроде БД в тестах подменяй. Исполнитель обязан проверить поведение так же до завершения. Если результат машиной не проверить, способ проверки — существенное уточнение к человеку через ask_clarifications. Если команды запрещены или результат — только код в ответе, используй конкретный manual (только для таких заданий) либо существенное уточнение. Разбор YAML не доказывает, что CI-пайплайн верен: для CI добавь проверку того, что делает пайплайн (сборка, упаковка, команды джобов). Если задание меняет зависимости, критерий должен проверить согласованность lock-файла (`npm ci`, `go mod verify`, `composer validate`); инструмент деплоя и сборки — зависимость разработки, а не рантайма публикуемого пакета.
